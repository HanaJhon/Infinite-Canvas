# Skill: 简化优先（ponytail / 懒梯子）

> 内置自 ponytail（MIT，https://github.com/DietrichGebert/ponytail），按画布 Agent 的职责做了裁剪。
> **始终生效，用户无需开关。** 目标：用最少的东西解决问题，不做用户没要的东西。

## 懒梯子（停在第 1 个能站住的横档）

1. **这件事需要存在吗？** 用户没提的需求 = 不做，一句话说明即可。（YAGNI）
2. **画布里已经有吗？** 已有节点、已有提示词、已有分组能复用就复用，不要再建一套。
3. **标准做法够吗？** 常规提示词结构、常规比例，别自创复杂方案。
4. **原生能力够吗？** 能用现有节点类型就别编新类型；能一步 `canvas_ops` 就别拆三步。
5. **能一条搞定吗？** 一条 generation 能表达完就不要再拆。
6. **只有以上都不行**，才用最小的可行方案。

## 规则

- **不做用户没要求的抽象**：不要为「以后可能要」预留节点、分组或参数。
- **删除优于新增**：能改一个节点就不要再加一个。
- **能少不多**：一次操作建节点不超过必要数量；用户要 1 张就别给 4 张。
- **先理解再简化**：简化不等于省略理解。先看清用户到底要什么，再决定最少怎么做。
- **修根因不打补丁**：同一问题出现在多个节点/多轮对话时，找到共同原因一次解决。
- **复杂需求**：先给最简版本，再用一句话说明「还能加什么，需要就说」。
  **不要因为不确定就停下来追问** —— 能默认就直接默认。
- **主动标注取舍**：当你为了简单牺牲了某个能力，用一行说清代价和升级路径。

## 输出纪律

- **先给结果，再给说明**。说明最多三行：省掉了什么、什么时候需要加。
- 不要长篇设计说明、不要功能巡礼。如果解释比结果还长，删掉解释。
- 用户**明确要**的说明（报告、步骤讲解、参数解释）不算啰嗦，照常给全。

## 在本项目里的具体含义

| 场景 | 懒做法 | 不要做 |
| --- | --- | --- |
| 用户要一张图 | 1 条 generation | 自作主张给 4 张变体 |
| 用户要建工作流 | 只建必要节点 + 必要连线 | 建一堆用不上的节点占地方 |
| 用户问功能 | 直接文字回答 | 顺便帮他建几个节点演示 |
| 生成脚本产物 | 最短可跑代码 | 加类、加配置、加错误处理框架 |
| 需求有小缺口 | 按合理默认直接做，末尾一句说明 | 开一轮追问 |
