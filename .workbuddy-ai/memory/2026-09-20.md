```

  ├─ 派生该副本：--apply-update <zip> <dest> <waitPids> <launchExe>
  └─ 自己退出（释放文件占用）

  ├─ 等 PID 退出 → 备份 → 解压 → 剪枝 → 删包

```

- 副本用完**无法自删**（它就是正在运行的映像）→ 由**下次启动的启动器**清理
  `data/_apply_update_*.exe`。
- ⚠️ `Main(string[] args)` 里 `--apply-update` 分支**必须排在单实例互斥量之前** ——
  此时旧启动器可能还没退干净，走正常分支会被互斥量挡下并弹「已在运行中」。

### 包内新增 `release-manifest.json`（`tools/release.py`）

`{format, version, kind, prune_roots, files:{relpath: sha256}}`，作为**虚拟 zip 条目**
塞进包内（`write_zip(..., extra=...)`）。

**为什么放包内**：避免让 C# 再维护一份目录清单（本项目已踩过「两处清单不一致」的坑）。
`prune_roots` 由 `PROGRAM_DIRS` 派生，是执行器剪枝的**唯一权威来源**。

### 执行器步骤（`launcher/UpdateApplier.cs`，374 行）

| 步骤 | 要点 |
|---|---|
| ① 等 PID | 启动器 + 服务，120s 超时；**超时即中止、不改盘** |
| ② 读清单 | 缺清单或 `kind != full` 直接中止 |
| ③ 备份 | 只备份「sha256 会变」的旧文件 → `data/update_backups/<时间戳>/`（日常几 MB，而非整目录 156 MB） |
| ④ 解压 | 剥掉包内顶层目录；**每条做路径越界校验**（防 `../` 穿越） |
| ⑤ 剪枝 | 只删 `prune_roots` 内且不在新清单里的文件；另有禁用名单（`data/assets/output/API/.git/.workbuddy-ai`）作二次防线 |
| ⑥ 收尾 | 删包 → 备份保留 10 个 → 拉起启动器 → 日志写 `%LOCALAPPDATA%\InfiniteCanvasLauncher\update.log` |

### 规则状态机（`normalize_version`）

```
parts = [a,b,c]
loop:
  over = [i for i,x in enumerate(parts) if x >= 10]
  if not over: break
  i = over[-1]                      # 取最靠右的溢出位
  if i == 0: parts = parts[:1]; break   # 首段溢出 → 截断，不再进位
  carry, parts[i] = divmod(parts[i], 10)
  parts[i-1] += carry
  if i < len(parts)-1: parts = parts[:i+1]   # 丢掉右边已归零的段
```

200 步连续进位实测：严格递增 ✓ / 规范式幂等 ✓ / 段数只减不增 ✓。

### 🚨 本轮两个严重踩坑（都出在自己写的钩子上）

1. **钩子崩溃 → 老板所有提交被堵死**（老板发截图来问「同步时报错」）：
   `scan_secrets.py` 原来用 `✔` / `✖`（U+2714 / U+2716）做状态标记，在
   **GBK 控制台（代码页 936）** 下抛 `UnicodeEncodeError: 'gbk' codec can't encode character`。
   pre-commit 钩子正是由 git 客户端以 GBK 环境拉起的 → 钩子崩、提交失败。
   → ① 状态标记一律 ASCII（`[OK]` / `[FAIL]`）；② `sys.stdout.reconfigure(errors="replace")` 兜底；
   ③ `_run()` 包一层：**脚本自身异常时返回 0 并打 `[WARN]`**（fail-open）——
   一个编码小 bug 不该把整个仓库的提交堵死，只有真扫到密钥才返回 1。
2. **扫描器「假阴性」——差点又得出「历史无密钥」的错误结论**：
   `ENV_LINE` 写成 `\s*[:=]\s*(.+?)`，`\s` **把换行也吃了** → `API_PROVIDER_FHL_KEY=`（空值行）
   与下一行的真密钥行被并成一个值 `'API_PROVIDER_GRSAI_KEY=415***561'`，含 `=` 于是被字符集检查拒掉
   → **真密钥凭空消失**。
   → 改成 `^[ \t]*(NAME)[ \t]*[:=][ \t]*(.*?)[ \t]*$`（分隔符两侧只许 `[ \t]`；值用 `.*?` 允许为空）。
   ⚠️ **教训**：规则收紧后**必须拿「已知含密钥的样本」做正控**，否则会把「漏报」当成「已干净」。
   🚨 **衍生教训（同日晚间发现）**：我为了讲清这个 bug，把真密钥原样抄进了
   `tools/scan_secrets.py` 的注释里 → **扫描器自己成了泄漏源**，还随发布包分发出去。
   **写注释/文档/日志一律用掩码值（`415***561`）**，真密钥只允许出现在被 gitignore 的 `.env` 里。

另外两个小修：`--batch` 输出要处理 `<sha> missing`（2 字段）头，写成
`if len(parts) != 3: break` 会**静默截断后续所有对象**；`SENSITIVE` 里 `AUTH` 要写成
`(?<!o)AUTH`，否则 `oauth2_redirect_url` 这类代码行会误报。

3. **`--history` 从未真正扫描过（提交 `cd2ebe3`）——最危险的一类 bug**：
   `iter_history()` 产出的路径形如 `API/.env @ b76dd86274c6`（**磁盘上不存在**），
   但 `main()` 里统一用 `os.path.isfile(ROOT/path)` 判断 → 每个条目都被 `continue` 掉 →
   **`--history` 永远报「干净」**，输出看着完全正常、结论完全错。
   修法：统一约定成 `(显示路径, 文本或 None)`，`None` 才去磁盘读，历史模式直接带 blob 文本。
   ⚠️ 这条与上面第 2 条是同一类错误的两次发生 —— **扫描器任何改动都必须拿已知阳性样本验证「真的扫到了」**。

### 验证

- **GBK 环境**下实测 `--tree` 与 `--path` 两条路径均不崩；`PYTHONIOENCODING=gbk git commit` 真实验证钩子正常

### 3) 技术备忘

- `api.github.com` 匿名调用**配额已耗尽**（403 rate limit）→ 改用 `releases/download/...` 的
  **HEAD 请求**量体积、**Range 请求**读 zip 中央目录，全程不消耗 API 配额、不下载整包。
- ⚠️ **ZIP 中央目录字段偏移**：压缩方式在 **10**、压缩大小在 **20**、未压缩大小在 **24**、
  本地头偏移在 **42**。踩过坑：把偏移 **12** 当成压缩大小（那是 `last_mod_time`），
  取错字节数 → 解压出残缺内容还误以为「密钥不同」。
- 从远端 zip 单取一个条目：Range 取中央目录 → 拿 `local_header_offset`/`comp_size` →
  Range 取「本地头(30+name+extra) + 压缩数据」→ `zlib.decompress(raw, -15)`。
