## §2 🚨 「先给 2-3 个方向」被系统提示词压死

- 现象：画像里明写「方案数量：先给 2-3 个方向」，模型照样只回 1 条 prompt。
- 根因：`agentSystemPrompt()` 的【出图数量】段在 `finalCount=1` 时硬写 `prompts 只返回 1 条`，
  与画像的「要多个方向就真的返回多条 prompt」直接冲突，模型服从了更靠后的那条。
- 修法：**把「张数」和「prompt 条数」拆成两件事** ——
  张数 = 每条 prompt 的 `count`；条数 = 方向数（用户记忆/本轮要几个方向就写几条）。
- 复测：`我们下个月新品上架，汽车座套要一套主图` → 3 个方向（A 白底 / B 座舱生活 / C 家庭出行），每条 count=1；
  `帮我画个橘猫` → 1 条且自动带上「生活场景图风格」；明确说「一张」→ 1 条。

## §3 🚨 出图永远 1:1 的真因（两层，都要修）

老板反馈：「模型不太听话，生成的图片是 1:1 的」。

**第一层：模型不照做，前端没兜底。**
- 实测：用户说「3:2」，模型返回的 prompt 里 `ratio` 仍是 `square`。
- 修法：新增 `parseExplicitRatio(text)` + `applyExplicitRatio()`，在 `parseAgentResponse()` 里
  **用用户原话确定性覆盖**所有 prompt / generation 的 ratio（模型只负责写提示词内容）。
- 支持：任意 `a:b` 按比例就近匹配白名单（偏差 >15% 不硬塞）；中文 横版/横图/横屏→landscape、
  竖版/竖图/竖屏→portrait、方形/正方形/方图→square。
- 另在 `agentSystemPrompt()` 补【比例 / ratio】段（列出 9 个 key 与对应比例）—— 之前提示词里**完全没提 ratio**，
  模型只能瞎猜。
- 顺带修：`generations` 直出路径原本不接 `ratio/resolution/quality`，现在和 prompts 一致。

**第二层（更隐蔽）：后端把精确约分结果直接交给上游。**
- `runninghub_aspect_from_size('3520x2352')` 做精确约分 → `220:147`，**不在 Grsai 白名单**，
  上游不报错、静默按 1:1 出图。⇒ 前端算对尺寸也没用。
- 修法：新增 `snap_aspect_ratio(value, allowed, tolerance=0.15)`，`grsai_aspect_ratio()` 的反推结果
  **必须再过一次吸附**；白名单里没有相近值时放宽到「最接近」，**至少保住横竖方向**（退成 1:1 是最差结果）。
- 实测映射：3520x2352→3:2｜2352x3520→2:3｜3264x2448→4:3｜2160x3840→9:16｜3840x1648→21:9｜1648x3840→9:16（原为 1:1）。
- **真实生图验证**：`size=3520x2352` → 出图 **5056×3392（1.4906 ≈ 3:2）**。Grsai 返回自己的原生尺寸，比例正确即可。

## §5 把 AI Agent 从「提示词优化器」改成「任务编排者」

老板原话：「理解模型不应该只处理提示词优化，而是应该先理解用户需求再进行任务的编排处理
（包括决定是否需要使用到图像模型和如何调整相关生图参数）以及后续如何合理调用画布功能和画布控制」

### 根因：只给了规则，没给事实
模型原来只知道「怎么写提示词」，不知道画布上有什么节点、有哪些生图通道和模型、画布动作有哪些。
没有这些事实，它只能退化成「写提示词」——**编排不是提示词能写出来的，是要有决策依据的**。

### 改了什么
1. **新增 `agentOrchestrationContext()`**（注入 system prompt，思维模式 + 直接模式都注入），四块：
   - 【可用生图能力】通道 id + 模型清单（≤8 通道 × 12 模型），明确「要换模型就写 provider/model，值必须来自清单」
   - 【画布现状】最近 24 个节点的 标题/type/有无内容/选中态/坐标
   - 【可用画布动作】canvas_ops 全部 op 与参数
   - 【能力边界】图能直接出；**视频/3D 只能建节点、不许谎称已生成**；文档走附件产物协议
2. **输出契约加 `intent` + `plan`**：
   `intent` = chat|generate|edit|video|document|canvas|mixed；`plan` = 给用户看的步骤数组（≥2 步才写）
3. **【身份】段重写成「编排四步」**：判需求 → 定能力（用不用图像模型/哪个/什么参数）→ 定落点（要不要动画布/放哪）→ 按序执行
4. **逐条通道/模型真的可用了**：`normalizePrompts` 校验 `p.provider`/`p.model` 是否存在（模型会编型号名），
   `runAgentGenerations` 按 `gen.provider`/`gen.model` 走，确认按钮与 generations→prompts 转换都要透传。
5. **plan 渲染**：`.agent-plan` 虚线卡片 + 序号步骤，≥2 步才显示（单步跟正文重复）。

### 🚨 顺带修掉一个把「多方向」彻底废掉的问题
执行层 `processAgentLlmResult` 原来只要「用户没要多张」就 `prompts.slice(0,1)` ——
**偏好记忆里的「先给 2-3 个方向」在真实 UI 里根本落不了地**（之前只在直连 API 测过，没走这层）。
改成三档：① 用户本轮说了数字 → 按数字截；② 没说但记忆要多方向（`agentWantsMultiDirection()`）→ 保留；
③ 都没说 → 才截 1 条。同时在提示词里写明「用户说了数量就以用户为准，记忆是默认值不是硬规矩」。

### 实测（真实模型 + 真实决策链）
| 输入 | intent | prompts | 结果 |
|---|---|---|---|
| 你好 | chat | 0 | plan []，无推销 |
| 帮我画一张3:2的虎斑猫 | generate | 1 | ratio=landscape（「一张」压过记忆的多方向）|
| 下个月新品上架，汽车座套要一套主图 | generate | 3 | plan 2 步，每条 square/4k/high |
| 在画布右边建提示词节点，标题叫"文案草稿" | canvas | 0 | 真建了 1 个节点，回复诚实 |

### ⚠️ 验证坑
- **别用 puppeteer 驱动完整 `sendAgentMessage()`**：流式 + WS 通知在无头环境会卡住不返回。
  可靠做法 = 先直连 `/api/agent-llm-task` 拿真实模型输出，再在页面里调 `processAgentLlmResult()`
  （拦截 `runAgentGenerations` 避免真花钱生图）。
- Grsai 网关偶发 `completion_tokens: 1` + 空文本（后端会兜底成「接口返回了空回复。」）。
  **同一输入重试即好**，别当代码 bug 排查。

## §6 输入框支持拖入 / 粘贴文件 + 内联引用 token + Ctrl+C 复制画布节点

老板要求：「允许小抽AI输入框中拖入文件、通过剪贴板粘贴文件、粘贴指令粘贴文件到语句的任意位置，
像 workbuddy 一样；允许 Ctrl+C 复制画布节点并粘贴到输入框，提交内容是小抽AI 可读取的节点内容
（目的是便于 agent 使用画布控制做针对性后续操作）」

### 原来缺什么
- 输入框 `paste` 只认 `image/*` ⇒ 粘 PDF / 视频 / xlsx **一点反应都没有**；
- 拖入/粘贴只能进附件条，**没法插到句子中间**；
- 复制节点后粘到输入框什么都没发生（`nodeClipboard` 被 `isEditableTarget` 挡掉）。

### 新增（全部在 `smart-canvas.js`）
- `agentInsertTextAtCursor(text)`：按光标插入；**挨着标点时不再补空格**（否则出现「[节点:a] ，」）。
- `agentAttachFilesInline(files)`：先 `agentAttachFiles`，再按「前后差集」把新增附件转成内联 token
  `[图:文件名]` / `[文件:文件名]` 插到光标处。
- `agentAddNodeRefs(nodes)` + `agentNodeRefFromNode()`：节点 → 引用对象（id/标题/type/坐标/文本/图片/3D/pending），
  插 `[节点:标题]`，上限 `AGENT_NODE_REF_MAX=8`，同节点去重。
- `agentNodeRefsContextBlock()`：发送时追加【用户引用的画布节点】对照表（含 prompt 正文），
  模型才知道 `[节点:xxx]` 是什么、能不能直接拿标题当 `canvas_ops` 的 id。
- `agentNodeClipboardText()` + `AGENT_NODE_CLIP_MARKER='【画布节点】'`：复制节点时写一份可读文本。
- `agentState.nodeRefs`（默认 `[]`）+ 附件条渲染 `.agent-attach-noderef`（虚线卡片，点卡片跳到该节点）。

### 🚨 两个关键判断
- **token 里写名称不写编号**：附件编号 = `agentLastResults().length + i + 1`，会随增删和上一轮出图漂移，
  写编号必然对不上；名称稳定，且发送时另附对照表。
- **复制走原生 `copy` 事件写剪贴板，不靠 `navigator.clipboard.writeText`**：后者在 WebView/非安全上下文会静默失败，
  拿不到 marker 就分不清「节点」和「普通文本」。同时给 `copy` 加了「有文字选区就不拦」的保护，
  否则会抢掉提示词节点里的文字复制。

### 粘贴路由优先级（`agentInput` 的 paste）
① 剪贴板有文件 → 附件 + token；② 文本以 `【画布节点】` 开头（或文本为空但有 `nodeClipboard`）→ 节点引用；
③ 其余不拦截，交给 textarea 原生插到光标处。

### 实测（无头 Edge）
- 光标插入：`把改成竖版` 光标在 1 → `把 [节点:主图] 改成竖版` ✓
- 复制两个节点→粘贴：`参考 [节点:主图] [节点:卖点文案] ，重新出一版`（已修掉标点前的空格）+ 2 张引用卡片 ✓
- 粘贴图片：`参考 [图:test-paste.png] 风格` + 附件入列 ✓
- 拖入图片：`参考 [图:drop-test.png] 做一张新图`，`drop.defaultPrevented=true`（没误建画布节点）✓
- 发送载荷含【用户引用的画布节点】对照表，`nodeRefs` 发完即清空 ✓
- 纯文本粘贴 `defaultPrevented=false`（原生行为保留）✓

### ⚠️ 测试坑
`copySelectedNodes()` 里有 `isEditableTarget(document.activeElement)` 判断，
无头测试里若焦点还在输入框会直接 return（表现为「复制没生效」）——**测之前先 blur**。
清理测试画布节点后必须 `scheduleSave()` 并等 3-4 秒，否则只改了内存没落盘。

## §7 🚨 Agent 生图完全没走遮罩（局部重绘失效）+ 附件改胶囊

老板反馈：「我原图是 1600x1600，生成的是 1024x1024，所以他完全没有按照遮罩功能处理任务，
而是直接生图；另外上传的文件名应该是胶囊形式，鼠标悬放时可以直接预览，而不是常驻显示」

### 根因（两层，缺一不可）
1. **`runAgentGenerations` 的请求体里根本没有 `inpaint` 字段** —— 只有
   `{prompt, provider_id, model, size, quality, n, reference_images}`。
   遮罩局部重绘只存在于 `runApiGeneration`（编辑器底部 composer）那条路径。
   ⇒ agent 出图永远是整图重画：原图被覆盖、尺寸按 `apiImageSize()` 走，和遮罩无关。
2. **模型不知道画布上有遮罩**：`agentOrchestrationContext` 的【画布现状】没标遮罩状态，
   提示词里也没有任何局部重绘的约定。

### 改了什么
- `agentResolveInpaintTarget(gen)`：按 `gen.target_node`（标题/id）在**有有效遮罩**的节点里找目标；
  没指定且画布只有一个带遮罩节点时自动用它。`validNodeInpaint` 会校验原图没被换掉/换序，失效就不硬走。
- `agentInpaintPayload(meta, refs, providerId, base)`：字段与 `runApiGeneration` 的 inpaint 分支**完全对齐**
  （`operation:'inpaint'` + `inpaint{base/mask/crop/crop_mask/bbox/base_w/base_h/aspect_ratio/size/feather}`，
  `size`/`aspect_ratio` 跟裁切走，`reference_images` = crop + mask + 其它参考图）。
- 占位节点逻辑：局部重绘**复用被遮罩的那个节点**（不新建），成功后才 `delete node.inpaint`。
  🚨 局部重绘不能改节点标题（`if(!gen._inpaintNodeId)` 才重命名）。
- `normalizePrompts` 接受 `inpaint` / `target_node`；确认按钮、generations→prompts 转换都要透传。
- 提示词加【局部重绘 / 遮罩】：只写「这块变成什么」，不写构图/光线，不写 ratio/count。
- 【画布现状】标「**已涂遮罩（可局部重绘）**」，并在末尾提示有 N 个遮罩节点。
- **兜底**：用户原话命中 `遮罩|涂抹|局部重绘|只改这|被遮挡…` 且画布只有一个遮罩节点 → 强制 `inpaint:true`。
  漏判代价是整图重画（原图被覆盖），比多判一次严重得多。
- 顺手修：`urls` 为空时不再标 `done`（改成 `error`），否则卡片显示「已完成」却一张图都没有。

### 实测
- 请求体：`operation:'inpaint'`、`size:'1536x1024'`、`aspect_ratio:'3:2'`、
  refs = [crop, crop_mask(role=mask)]，bbox `[500,600,601,401]` ✓
- **真实跑通**：原图 1600×1600 + 遮罩 → 产出 `inpaint_merged_*.png` **1600×1600**，
  视觉上只有遮罩区域变成红色背带，其余像素与画幅完全没动 ✓
- 节点图被替换成回贴后的整图、`node.inpaint` 已清 ✓

### 附件改胶囊（老板要求「默认隐藏」）
- 新样式 `.agent-attach-pill`：24px 高胶囊 = 编号 + 图标 + 文件名 + ×，**不再常驻缩略图**。
- `.agent-attach-pop`：悬停才出现的预览卡（图片/视频缩略、文档卡片+「作为 Skill 载入」、节点 type/坐标/正文摘要）。
- 实测：3 个胶囊高度均 23px；悬停首个出现 158×172 预览卡且含 img ✓

### ⚠️ 清测试产物要**逐个点名删**
`assets/output/inpaint_*`、`assets/input/inpaint_*` 里有大量是**老板真实使用的素材**，
绝不能按通配符清。本次只删了自己 mask-prepare / 生成的 9 个具名文件。

## §8 输入框改 contenteditable —— 附件内嵌成胶囊（老板：「能否直接内嵌到文案中？」）
### 为什么必须换
`<textarea>` 只认纯文本，塞不进 DOM 胶囊。要让附件「长在句子里」，输入框本身必须是 `contenteditable`。
### 改造方式（关键取舍）
- **不重写 20+ 处调用点**，而是加一层垫片 `installAgentInputShims()`：
  `Object.defineProperty(agentInput,'value',{get:agentInputPlainText,set:agentInputSetText})`，
  外加 `disabled` getter/setter。老代码 `agentInput.value = '...'` 全部照旧能用。
- `agentNodesToText(root)`：chip → token，`<br>`/`<div>` → `\n`（复制的文本靠它还原）。
- 光标操作不能用 `selectionStart`：新增 `agentCaretRange()` / `agentTextBeforeCaret()` /
  `agentDeleteCharsBeforeCaret(n)` / `agentInsertTextAtCursor()`。
- 状态 ↔ DOM 对账：`syncAgentInlineChips()`（`renderAgentAttachments` 末尾调），
  删除胶囊用 `agentRemoveChipByKey()`，并按句子顺序回写状态数组 `agentSyncStateOrderFromChips()`
  （**参考图顺序决定上游拿哪张当基准图**，顺序错＝改错图）。
- placeholder 靠 `data-empty` + `::before`，因为 contenteditable 不吃原生 placeholder。
### 🚨 两个坑
- `agentInsertChipAtCaret` **不能无条件 focus**，否则页面加载时抢焦点、把用户正在别处输的东西打断。
- `insertAgentMention` 要先删掉用户打的 `@过滤词`（`lastIndexOf('@')` → 删到光标），否则残留 `@主` + 胶囊。

## §9 Agent 掌握全部画布能力（老板：「而不是需要用户提供明确功能或关键触发词时才处理」）
### 做了什么
1. `applyAgentCanvasOps` 从 5 个 op 扩到 **9 个**：新增 `focus_node` / `group_nodes` / `ungroup_node` / `arrange_nodes`。
2. `agentOrchestrationContext()` 新增【画布能力总览】：**意图 → 能力**的映射表，
   能做 / 只能引导（🖐）分开标，让模型按"用户想达成什么"路由，而不是等关键词。
3. 「编排四步」加三条硬约束：不要等功能名；**说了就必须给 op**；整理/归组/对焦**不许反问**。
### 🚨 核心教训：**提示词治不了「漏给字段」，必须代码兜底**
实测原样（修复前）：
```
「这几个图看着有点乱」→ intent:"canvas"、plan:["按连线关系整理画布节点"]、
                        reply:"我会按连线关系把画布节点整理开"、canvas_ops:[]   ← 听懂了，没落地
```

模型看不见自己漏了字段，加多少条提示词都会漏。于是新增 `deriveCanvasOpsFromIntent(text, reply, intent, plan)`：
把模型**已经表态的意图**反推成 op。只派生**安全、可撤销、无歧义**的三类（整理 / 归组 / 对焦），
建节点、改标题这种要具体参数的**一律不猜**——猜错比不做更烦。
派生成功把 reply 的「我会…」改写成「已…」；派生不出来才把话收回（加「这一步我没能真正执行」）。
### 三个真 bug（都是这轮实测才暴露的）
- `_doneClaim` 只认 `已(创建|归为…)`，**漏了中间夹宾语的写法**「已将两个节点归为一组」→ 放宽为
  `已(将|把).{0,12}(动词)`。

  → 退回**整张画布**。
- 案例 #3「这张图里那件衣服换成蓝色」→ 模型反问「要把哪一张图」。加确定性消解：
  **有图节点去重后只有 1 个**时指代无歧义，直接把追问改成 `edit` + `use_last_outputs`（实测通过）。
### 实测
- 确定性输入（模型原样输出灌进去）：3 个案例全达标 —— 整理**真移动了 3 个节点**、

## §14 没涂遮罩也能局部改 —— 理解模型自动出框造遮罩
### 老板需求
「当没有涂抹遮罩时，能否由理解模型自动涂抹遮罩位置」
老板拍板两个取舍：① **只要模型能定位就自动**（不限于"明确局部语义"）；② **直接出图**，不先确认框。
### 结论：能做，而且后端一行没改
现有局部重绘的入口就是「一张 mask PNG」：
`mask.png → /api/image-mask-prepare（算框/扩比例/裁切/羽化/出 overlay）→ node.inpaint → 生成 → 回贴`。
所以自动遮罩的全部工作量 = **在第一步之前把那张 PNG 造出来**，后面整条链路原样复用。
### 必须先补的前提：模型根本看不见 @引用的节点图（真缺口）
`agentNodeRefsContextBlock()` 只给模型**文字**（标题 / 类型 / 图片 URL 字符串），
图本身只进了生图接口的 `reference_images`（`agentNodeRefImages`），
**从没进过理解模型的 `images`**。⇒ 模型没见过那张图，就判断不了「这只猫在哪」。
新增 `agentAppendNodeRefImagesToContext(contextImages)`，两处 `contextImages` 构建都调用。
### 改动（前端 9 处，后端 0 处）
1. `AGENT_OFF_MODE_INSTRUCTION`：输出格式加 `"mask_hint":null`；加「什么时候填 / 什么时候留 null」判定规则。
2. `agentNormalizeMaskHint(raw)`：**严格校验**，只认 0~1 归一化。
3. `agentApplyMaskHintInto(target, raw)`：搬 hint 并**自动置 `inpaint:true`**
   —— 不要求模型同时写两个字段（上轮就是被"多一个必填字段多一处漏搬"坑过两次）。
4. 四条转换链全部补 `mask_hint`：`generations.map` / `normalizePrompts` / 思维模式 `gen→prompts` / `_triggerGenerationsIfAllDone`。
5. `agentBuildMaskBlob`：加载原图 → 黑底 + **白矩形**（后端 `inpaint_mask_bbox` 认 `>=128` 为要改）→ PNG。

## §15 遮罩痕迹保留 + 只有手动/明说要才清 + 画笔圆环光标
### 老板需求（三条）
1. 用遮罩生完图**不要自动清除遮罩痕迹**；
2. 只有**手动清除**或**明确要求 Agent 清除**时才清；
3. 涂抹遮罩时鼠标在画面中**以圆环显示画笔大小**。
### 先摸清「生成后清遮罩」到底有几处
全库 `delete *.inpaint` 共 **6 处**，其中 3 处是生成后清的：
| 位置 | 路径 | 处理 |
|---|---|---|
| L21771 | 主链路（pending 恢复分支） | **删掉** |
| L21781 | 主链路（正常分支） | **删掉** |
| L29986 | agent 路径 | **改成迁移**（见下） |
保留的 3 处（合法）：删图 `L15560`、换图/裁剪/画笔 `L18029`、手动清除 `clearNodeInpaint` `L18214`。
### 🚨 两条路径落图位置不同 —— 这是本次最关键的区别
- **主链路（composer 直接运行）**：`shouldCreateBranchOutput = groupRun || (nodeHasImages && !workflowModeRun)`
  ⇒ 局部重绘**也是新建分支节点**放回贴结果，**原节点的图原封不动**。
  所以只要把 `delete node.inpaint` 删掉，遮罩就自然保留在原节点上（`base_key` 仍对得上）。**不需要迁移。**
- **agent 路径**：`gen._inpaintNodeId` 是**原地改**，`liveNode.images = urls` 直接顶掉原图
  ⇒ 原图 URL 变了 ⇒ `validNodeInpaint` 的 `base_key` 检查必然失败 ⇒ **「不清」也等于清了**（遮罩直接看不见）。
  必须用**新图 + 原 mask** 重跑一次 `/api/image-mask-prepare` 把遮罩迁过去。
### 新增：`rebaseInpaintOnImage()` / `keepInpaintAfterRun()`
- 放在 `validNodeInpaint` 之后；用 `prevMeta.mask_url`（原始整图遮罩）→ 新图 base → prepare → 得到新 crop/crop_mask/overlay/bbox。
- 尺寸天然对得上：**回贴保证输出 == 原图尺寸**，mask 依然对齐。
- 失败返回 null，**保留旧 `inpaint` 不动**（用户重涂即可，不会更糟），并 `console.warn` 留痕。
- 🚨 agent 里 `await keepInpaintAfterRun(...)` 必须放在 `undoSuppressed = false;` **之后** ——
  这次要发一次 prepare 请求（几百 ms），放抑制区间里会把老板这期间的撤销一起吞掉。
### 新增：Agent 清除遮罩 = `canvas_ops` 的 `clear_mask`
- `applyAgentCanvasOps` 加分支（别名 `remove_mask` / `clear_inpaint`）：写 `id` 清那个，不写清全部。
- 🚨 用 `delete n.inpaint` 而不是 `clearNodeInpaint()`：后者会 toast + 逐个 `pushUndo()`，
  一批清多个会塞一堆撤销栈，外层已经 `pushUndo` 过了。
- prompt 两处登记：`【可用画布动作】` 列表 + `【能力总览】`（并要求模型**别主动清遮罩**，
  只有用户明确说「不要这个遮罩了」才清）。
### 新增：画笔圆环光标
- `brushCursorActive()`：`mask` 模式，或 `brush` 模式且 `brushTool === 'free'`（矩形/椭圆/文字不需要）。
- 元素 `#editBrushCursor`：`position:fixed` + `pointer-events:none` + **双层描边**
  （内 `rgba(0,0,0,.8)` 外 `rgba(255,255,255,.95)`）—— 遮罩是半透明白，浅底上白圈看不见。
- 🚨 **圆环尺寸必须按屏幕像素算**：`editBrushSize() * (rect.width / canvas.width)`。
  直接拿 `editBrushSize()` 当 CSS 尺寸，图片缩放后圆环和真实笔触就对不上。
- 绑定：`pointermove` 单独挂一个 `syncBrushCursor`（`moveEditDraw` 不按下时 early-return，靠它带不出来）；
  `pointerleave` → `hideBrushCursor`；`maskBrushSize`/`paintBrushSize` 的 `input` → `refreshBrushCursorSize`
  （拖滑块时鼠标没动也要立刻跟上）；`closeImageEditor` 与 `setImageEditMode` 都要 `hideBrushCursor()`。
- 用**内联 style** 而不是改 CSS 文件：省掉「改 CSS 必须同步 `?v=`」那条坑。
### 实测（一次性画布 `ad6391e9…`，pageErrors 0，17/17 PASS）
- T1 造遮罩 → 换图（模拟生成）→ `validNodeInpaint` **确实失效** → `keepInpaintAfterRun` → **重新有效**，

## §16 老板报「仍然没能自动调用遮罩」—— 根因：思维模式的输出契约里没有 mask_hint

老板截图（16:51）报错原文：**「找不到要局部重绘的节点（遮罩可能已失效或对不上）」**。

### 根因（一句话）
Agent 有**两套输出契约**，我上轮只给「直接模式」那份加了 `mask_hint`，**漏了「思维模式」那份**。
老板走的是思维模式（有「提示词确认」卡片），模型严格照内联 schema 输出 ⇒ 只标 `inpaint:true`、不给 `mask_hint`
⇒ `agentAutoMaskGenerations` 的 todo 过滤 `agentNormalizeMaskHint(g?.mask_hint)` 为 null ⇒ 不造遮罩
⇒ `agentResolveInpaintTarget` 返回 null ⇒ 抛 29966 那句错误。

- 思维模式契约在 `agentSystemPrompt()` 里**内联**（L27779 `【输出格式 / Output Format】`），
  不在 `AGENT_FORMAT_INSTRUCTION`(L25060) / `AGENT_OFF_MODE_INSTRUCTION`(L25120) 里。
- 🚨 **铁律：凡是给模型加字段，两套契约 + 顶层兜底 三处一起改。**
  两套 = 思维模式内联 schema、直接模式 `AGENT_FORMAT_INSTRUCTION`；
  兜底 = 解析后如果 `data.mask_hint` 存在但每条 prompt 没有，补到每一条上（模型常放错层级）。

### 改了什么
1. L27789-27797 思维模式 `prompts` 字段说明 + 示例 + 判定规则（要填/不要填），末尾那句「顶层不用写」。
2. L25061/25065 `AGENT_FORMAT_INSTRUCTION` schema 补 `"mask_hint":null` + 字段说明。
3. L28292 patch 加顶层 `mask_hint` 兜底。

### 顺手修的一个数据安全问题（比根因更危险）
`runAgentGenerations` 的 catch（L30140）在失败时 `nodes = nodes.filter(n => n.id !== placeholderId)`。
局部重绘时 `placeholderNode` 就是**老板自己的节点**（`ipTarget.node`），
⇒ **任何一次上游报错都会把他原图节点删掉**。`recoverAgentGenerations` 的 catch 同病。
修：`if(gen._inpaintNodeId){ 只清 pending + runTimerHidden } else { 才删占位节点 }`。

### 实测
- **探针（真实调 Grsai `gpt-6-astra`，思维模式）**：模型返回
  `prompts:[{...,"inpaint":true,"target_node":"上传","mask_hint":{"target_node":"上传","bbox":[0.13,0.27,0.36,0.46]}}]`
  ⇒ 解析后 `prompt0.mask_hint` 有值、`inpaint:true` ✓（测试图红圆在左侧，bbox 基本吻合）
- **确认链路 e2e（11/11 PASS，pageErrors 0）**：`_triggerGenerationsIfAllDone` → 确认的 prompt 带 mask_hint
  → 自动造遮罩（`auto:true`, `bbox=[156,234,432,432]`, `size=1536x1536`）→ 请求 `operation:'inpaint'`、
  `reference_images` 2 张、**尺寸不是 1024×1024**；故意让请求失败后**节点还在、遮罩还在**（可重试）。

### 环境坑（下次省时间）
- Grsai chat **极慢**：只回「OK」要 19s；9.3KB system prompt + 图要 2~4 分钟，
  偶发 `Server disconnected without sending a response`。探针轮询上限要 ≥300s，puppeteer 要 `protocolTimeout:300000`。
- 测试拦截 `/api/canvas-image-tasks` 时**必须 reject**，不能 `new Promise(()=>{})`：
  后者会让 `runAgentGenerations` 永远 await 在 `Promise.all`，页面 evaluate 直接超时。

## §18 「Agent 不知道自己是怎么处理的图」= 历史里根本没传做法

老板截图（17:5x）：问「是不是用遮罩局部重绘的」，Agent 答「当前画布中无法确认是哪一种处理方式」。
老板原话：**「这很不合逻辑啊」**。

### 一、根因（不是逻辑问题，是信息没给）
`agentHistoryMessages()`（约 L28048）给模型的 assistant 历史**只有一句**：
```
[generated N image(s) with prompt: ...]
```
**做法、目标节点、遮罩位置、尺寸、成败，一个字都没有。**
模型只能去画布找线索（「这个节点现在有没有遮罩」），而遮罩会**迁移到新图 / 被清掉 / 被用户重涂**
⇒ 画布现状 ≠ 当时做法 ⇒ 只能答「无法确认」。

### 二、修法：自己记「当时怎么做的」
1. **`runAgentGenerations` 里落 `gen.exec`**（`_ipMeta` / `_ipNode` 已就绪、`throw` 之后）：

2. **`agentExecRecordLine(gen, idx)`** 把 exec 渲染成一行

   —— 老记录没有 `exec` 时从 `target_node` / `_inpaintNodeId` **反查节点标题**兜底。
3. **`agentHistoryMessages()`** 把它拼在 `[generated ...]` 后面（`g.exec || g.inpaint || status==='error'` 才拼）。
4. **`agentSystemPrompt()` 注入「【执行记录 / Execution Log】」块**：
   要求照记录直答；🚨 **禁止拿画布现状反推做法**；🚨 **禁止答「无法确认」**（老记录就说「没留下做法信息」+ 给能确认的）。
5. **`agentGenCardHtml`** 卡片状态栏也标 `遮罩局部重绘 · 上传` / `整图重绘`，老板肉眼可见。

1. **`agentOrchestrationContext()` 的画布现状只给标题、不给 id**

   只能写标题；标题重复 7 次 ⇒ 系统按「只认唯一命中」的规矩必然放弃。
2. 模型偶尔只标 `"inpaint":true` 不给 `mask_hint`（它按提示词「拿不准就让用户涂」），
   代码则按局部重绘去找目标 ⇒ 报错。**提示词和代码在这里自相矛盾**。

### 二、修法
- **画布现状 / 引用块都给 id**：`- 「上传」 id=smart_4toaqg type=…`、`[节点1]「上传」 id=up_2 …`；
  提示词四处同步改成「target_node **写 id**，标题只在唯一时可用」。
- **`agentCleanNodeRef()`**：剥 `#` / `id=` / `节点=` / 引号 —— 模型写法五花八门，不剥就匹配不上。
- **`agentPickAutoMaskNode` 增加「标题 ∩ 用户引用」**：7 个同名时用 `nodeRefs` 消歧（原来直接放弃）。
- **`agentExplainInpaintMiss()`**：失败文案不再说废话，直接说「画布上有 7 个节点都叫「上传」，
  我没法确定改哪一个 —— ① @ 引用那一张 ② 在那张图上涂遮罩」；能定位到唯一候选时**自动选中 + 聚焦**。
- 🚨 `agentAutoMaskGenerations` 失败时**不再 `delete gen.inpaint`**：删了以后任何重试都会变成整图重画。
