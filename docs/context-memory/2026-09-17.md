## 堵住「旧页面整份覆盖画布」的口子（`main.py`）

- 根因确认：`update_canvas()` 里的冲突判断写成 `if payload.base_updated_at and current_updated_at and ...`——**base 为 0 时整个条件短路、直接放行**，而 PUT 是全量替换（`canvas["nodes"] = payload.nodes`），所以一个没带 base 的陈旧页面能把服务端节点整份抹掉。这正是 09:55:56 那次 45 个节点归零的形态。
- 修复（`main.py:18176` `update_canvas()`）：
  1. 抽出 `base_updated_at = int(payload.base_updated_at or 0)`，原有「旧 base → 409」逻辑不变。
  2. **新增「静默丢节点」守卫**：`current_updated_at` 存在且 `base_updated_at != current_updated_at` 时，比较服务端与本次载荷的节点 id 集合；只要会删掉服务端已有节点就返回 409（带 `dropped_node_ids`）。前端 `smart-canvas.js` 的 409 分支本来就会 `mergeSmartNodeLists`（按 id 取并集，「宁可复活也不丢结果」）后用服务端 `updated_at` 当新 base 重存，所以合上即可，不会死循环。
- 边界：`base` 与当前一致时**正常删除节点照旧放行**（单页正常操作不受影响）；首次写入（服务端无节点）不受影响；只有「并发 + 丢节点」才拦。

## `canvas.js` 改标题/改图标会清空 logs 和 settings

- 现象：`setCanvasTitle()` / `setCanvasIcon()` 走的是 `PUT /api/canvases/{id}`，但载荷只带 `title/icon/nodes/connections/viewport`。服务端对 `logs` 和 `settings` 也是**无条件覆盖**（`canvas["logs"] = payload.logs[-500:]`、`canvas["settings"] = payload.settings or {}`），默认值 `[]` / `{}` → **重命名或换图标会把该画布的日志和设置清空**。
- 修复：

### 对项目运行与功能的影响：**无**

### 建议

1. **不跑 `gc`** —— 收益 0，还带事故风险
