## 二、对话标题可重命名

老板：**「允许重命名对话标题」**（截图箭头指向对话列表第一项）。

### 🚨 真正的坑：标题优先级反了
```js
// 原来
const title = firstMsg ? String(firstMsg.text).slice(0, 30) : (conv.title || '对话');
```
`conv.title` **只在没有消息时才生效** —— 也就是说存了也白存，改完刷新又变回首条消息。
改成 `customTitle || autoTitle`（用户改过的优先，没改过才跟随首条消息）。

### 另外两处连带问题
1. **`agentNewChat` 写死了 `title:'新对话'`** → 配合新优先级，新对话会永远显示「新对话」。
   改成 `title:''`（空 = 用首条消息自动生成）。
   老数据里已有的 `'新对话'` 在渲染时过滤掉（当「没起过名」处理），不用改盘。
2. **`.agent-chat-item` 是 `<button>`** → 里面要嵌 `<input>` 和删除按钮，是非法 HTML，浏览器会改写 DOM。
   改成 `<div role="button" tabindex="0">`，CSS 补 `width:100%; box-sizing:border-box`。

### 交互
- **双击标题**就地变输入框（预填当前显示的那行字，全选），`Enter` 保存 / `Esc` 取消 / 清空 = 恢复自动标题。
- `commit()` 用 `done` 标志防重入 —— `Enter` 之后还会触发 `blur`，不防会存两次。
- 输入框的 `click/dblclick/pointerdown` 都 `stopPropagation`，否则点进去就把对话切走了。

## 三、加「思考强度」档位

老板：在生图模型 pill 右边加一档「思考强度」。

### 先搞清楚的事实
`thinkingMode` 是个**布尔开关**（且被 `enforceAgentAlwaysOn()` 强制 true），
它控制的是**工作流**（先出提示词确认卡 vs 直接出图）+ 换一套系统提示词，
**跟模型内部推理深度无关**。`main.py` 里原来**没有任何** `reasoning_effort` / `thinking` 发送代码，
只读取返回的 `reasoning_content`。所以模型一直用它自己的默认档位。

### 实现
- **UI**：第三个 pill `#agentReasoningBtn`（`brain` 图标）+ 独立小面板 `#agentReasoningPanel`，
  5 档：自动 / 最低 minimal / 低 low / 中 medium / 高 high。复用 `showDropdown()` 定位。
- **状态**：`agentState.reasoningEffort`，默认 `'auto'`，存 localStorage。
- **转换**：`agentReasoningEffortForLlm()` —— `auto` 返回**空串**，其余原样。
  三处 `llmPayload` 构造（普通 / 流式 / 重新生成）统一加 `reasoning_effort`。
- **后端**：`CanvasLLMRequest.reasoning_effort` 字段 + `apply_reasoning_effort(body, effort)`，
  只在 `canvas_llm` 与 `canvas_llm_stream` 的**两处** `req_body` 注入。

### 🚨 关键决策：auto 一律不传参
不少 OpenAI 兼容网关不认 `reasoning_effort`，无条件塞会直接 400，把本来能跑通的请求搞挂。
所以只有用户**明确选了档位**才透传；`auto` / 空串 / 非法值一律不加字段。

### 覆盖范围（要跟老板说清）
- ✅ OpenAI 兼容 `chat/completions`（老板用的 `ep_...` 就属这类）
- ❌ **codex CLI 通道**（`codex_chat_text` → `run_codex_cli`，走本地 CLI，不经过 HTTP body）
- ❌ **gemini-cli 通道**（同上）
- ❌ Gemini 的 `thinkingBudget`、Anthropic 的 `thinking.budget_tokens` 是另一套参数，没做

## 四、纯提问不再触发生图（要「机制」，不要只堆提示词）

老板：**「他似乎仍然容易自动触发生图…能否不要一味用提示词做限制，而是让 agent 通过思考做判断
用户的真实需求，当真实需求与生图无关时不再直接触发生图窗口选项」**。
截图：问「DSC08366.JPG 这张图能看出来吗」→ 模型答出了汉兰达（对的），
但下面同时出现「正在生成图片…」+「📝 提示词确认 · #1 这张图能看出来吗」。

### 根因：判定词表漏了口语，不是提示词不够
- `AGENT_ASK_MARK_RE` 只有 `[？?]\s*$` —— 用户**没打问号**，句尾是「吗」⇒ `isQuestionOnly` = false
- `AGENT_UNDERSTAND_RE` 里没有「看出来 / 看得出 / 认得」⇒ `isUnderstandOnly` = false
- 于是 `looksLikeGenRequest` 因含「图」判成生图需求

### 修法：三层，主力是代码硬规则
1. **扩词表**（第一道）：`AGENT_ASK_MARK_RE` 加 `[吗呢]\s*$`；
   `AGENT_UNDERSTAND_RE` 加 `看出来|看得出|看出|认得|认得出|分辨|确认一下|能确认`。
2. 🚨 **硬规则（真正的机制，2026-10-22 新增）**：**不判断意图**，只看两个客观事实 ——
   ① 用户这句话里没有任何生图/编辑动作词（`agentUserHasGenAction()`）；
   ② 模型给的 prompt 就是用户原话（或原话一部分，≥8 字）。
   同时满足 ⇒ 一定是「把问话当提示词」⇒ 直接丢。
   **这条不依赖意图分类准不准**，词表覆盖不到的口语也能拦住 —— 正是老板要的「机制」。
   ⚠️ 有动作词时不动：「画一只猫」的 prompt 就是原话，但那是真需求。
3. **提示词辅助**（第三层，不是主力）：在 `AGENT_FORMAT_INSTRUCTION` 核心规则 2 后面加一句
   「只是在提问/让你看图时，prompts 和 generations 都必须留空」。
- `agentUserHasGenAction()` 必须定义在**顶层**（`looksLikeGenRequest` 之前），
  放函数内部测试访问不到（第一版就踩了）。

### 验证

8 条判定（能看出来吗 / 这是什么型号 / 描述这张图 / 看得出这是什么车吗 → 无动作；
帮我画一张 / 改成蓝色 / 画一只猫 → 有动作）+
端到端 4 条（纯提问 prompts 清空 / 无生图任务 / **分析文字保留** / 纯理解连改写过的 prompt 也丢）+

## 五、生图默认出 1024×1024（不是老板要的 4K 高质量）

老板：**「生图似乎默认用的是 1K 分辨率、1:1 比例，不是我要求的默认 4K 分辨率高质量」**（截图两张都是 1024×1024）。

### 排查：默认值本身是对的
`__res_probe.js` 实测：`agentState = {genRatio:'square', genResolution:'4k', genQuality:'high'}` ✓
`gpt-image-2.5-sunburst` + square + 4k → `2880x2880` ✓（该系列 4K 上限就是 2880，不是 4096）
`__size_probe.js` 实测「不指定参数」的 payload：`size=2880x2880, quality=high` ✓

### 根因：模型自作主张覆盖
`_genRes = gen.resolution || agentState.genResolution || '4k'` —— 只要模型在 generation 里写了
`resolution:'1k'`（它把 1K 当「安全默认」），就把老板的 4K 顶掉了。
质量同理（`gen.quality || 'medium'`）。**而界面上早就没有参数选择器了，他连改都改不了。**

### 修法：参数以**用户原话**为准，模型的建议一律不采信
- 新增 `agentExplicitResolution(text)` / `agentExplicitQuality(text)`（顶层）：
  只认明确说法 —— `4K/2K/1K/8K`（带 `(^|[^0-9])` 前置，避免把「24K」这种数字串误判）、
  `超高清/最高画质 → 4k+high`、`高质量/高清/精细 → high`、`普通画质 → medium`、`草稿/快速出图 → low`。
- `runAgentGenerations` 里改成：
  ```js
  const _genRes = agentExplicitResolution(_userText) || agentState.genResolution || '4k';
  const genQuality = agentExplicitQuality(_userText) || agentState.genQuality || 'high';
  ```
  **`gen.resolution` / `gen.quality` 不再参与**（跟 BH.7 的比例覆盖同一个思路：用户没说，别让模型替他决定）。
- `gen.ratio` 保持原样（模型给比例通常有画面依据，老板这次也没抱怨比例）。

### 验证
`__res_priority_test.js` **14/14 PASS**：
9 条判定（4K/2K/1K/没说/8K/高质量/普通画质/草稿/没说）+ 5 条端到端：
**模型硬塞 `resolution:'1k' + quality:'medium'` → 实际出 2880×2880 / high** ✓
用户明说 1K → 1024 ✓；明说 4K → 2880 ✓；明说草稿 → low ✓。
回归全绿：sizeguard 23、famsize 32、editmsg 28、inpaint_newnode 10、ask_no_gen 15、
model_pills 12、reasoning_effort 16、attach_mask 9。

## 七、上下文指代：「基于描述文案」被理解成「按参考图」

老板截图：先问「描述这张图的背景」→ 模型答了一段背景描述；再说「基于描述文案生成图片」→

### 排查：信息没丢，是理解错
`agentHistoryMessages()` 里 assistant 的 `content = m.text` —— 那段描述**就在历史里**，模型能看到。

## 八、允许 agent 并发：A 对话跑着时能去 B 说话

老板：**「允许 agent 并发，在 agent 连续对话处理中时允许用户新建对话进行新对话」**。

### 现状：按钮本来就没禁用
`#agentNewChatBtn` 一直是可点的（`agentNewChat()` 里没有任何 `agentThinking` 拦截）。
**真正的问题是结果归属** —— `processAgentLlmResult` 把回答 push 到 `agentState.messages`，
而用户切对话后这个指针已经指向 B ⇒ **A 的回答会串进 B**。

### 修法：给每条请求记「它属于哪个对话」
- `agentSendMessage` 发请求前：`userMsg._convId = activeConversationId;`
  `agentState._runningConvId = activeConversationId;`（两处入列点都加了）
- 新增 `agentPushAssistant(msg)` 取代原来 10 处
  `agentState.messages.push(assistantMsg) + slice(-AGENT_MSG_MAX)`：
  - 目标 = `msg._convId || _runningConvId || activeConversationId`
  - 目标 ≠ 当前对话 ⇒ push 到那个对话的 `messages`、`saveAgentState()`、
    轻提示「另一个对话有新回复」，**不刷新当前 UI**
  - 否则照常 push 到 `agentState.messages`
- `assistantMsg` 对象加 `_convId`（主路径 2 处），双保险。
- 生图阶段不用改：它改的是**画布节点**（全局共享）和 `assistantMsg` 对象引用（已在正确对话的数组里）。

### 已知限制（记下来，别再踩）
A 跑着 → 切 B → **又在 B 发了一条** ⇒ `_runningConvId` 被 B 覆盖，
此时 A 的结果若晚到可能落到 B。用 `assistantMsg._convId` 缓解了主路径，
但 10 处写入点里只有 2 处带这个字段。要彻底解决得把 convId 一路传到每个 push 点。
