    **只备份被覆盖的文件**。
  - 网页端 `manifest.json`（format 2）：`state`/`kind`/`created_at`/`from_version`/`target_version`/
    `source`/`parent_backup`/`update_notes`/`root_files{rel:{existed}}`/`static_snapshot`/`affected_files`。

### 2. 定位并修复「数据丢失隐患」（本轮最重要）

`main.py:rollback_update` 只要发现 `备份/static/` 存在就 `rmtree(static)` + `copytree`。
而 **legacy 恢复点只备份部分 static**：

| 恢复点 | 备份的 static | 体积 |
|---|---|---|
| `20260920-165128` | 18 文件 | 2 MB |
| `20260920-183530` | 14 文件 | 1 MB |
| `20260921-174211` | 18 文件 | 3 MB |
| **static 全量** | **74 文件** | **9.1 MB** |

→ 一旦用网页端回退启动器的恢复点，会**把 static 里未被备份的文件全删掉**。

**修法**：引入 `static_snapshot.complete` 标记 —— 只有 `true` 才允许整目录替换；
否则**逐文件复制，绝不删除**（`main.py:rollback_update` 的 `static_complete` 分支 /
`UpdateApplier.RestoreStatic`）。

### 3. 其余关键改动

- **`existed=false` 语义**（「更新前不存在」= 更新新增的 → 回退时删掉它）。
  🚨 连带修正 `UpdateApplier.Run` 顺序：**先算 deleteList，再建恢复点**，最后才
  `ExtractOverwrite` + `DeleteFiles`。原来「先覆盖再剪枝」→ **被删的文件进不了备份**。
- **回退白名单比更新更宽**：新增 `rollback_allowed_file()` / `safe_rollback_target()`
  （更新的 `update_allowed_file()` 信任边界是「网络下载」，回退来源是「本机恢复点」）。
  否则回退启动器备份时 `Lochou启动器.exe` / `launcher/` / `tools/` 会被**静默跳过**。
  两边都加 `ForbiddenRoots` / `ROLLBACK_FORBIDDEN_ROOTS`
  = `{data, assets, output, API, .git, .workbuddy-ai}`。
- **可再回退**：回退前先做安全快照（`kind="rollback_safety"`，目录名带 `rollback-` 前缀）；
  `create_update_backup(..., wide_scope=True)` 让它能涵盖 exe。
- **回退执行架构与更新同构**：启动器把自己复制成 `<root>/data/_apply_update_<pid>.exe`，
  以 `--rollback <name> <destDir> <waitPids> <launchExe>` 派生脱离进程 → 等 PID 退出 →
  还原 → `Relaunch`；本体 `ScheduleExit(1500)`。

### 6.1 改法：版本比较只留在 C# 侧（`localAhead`）

🚨 **不在前端比版本号** —— 版本规则只有 `tools/versioning.py` 与 `launcher/VersionUtil.cs` 两处权威，

- C# `HandleUpdateCheckAsync` 的返回体新增 `localAhead`：
  ```csharp
  localAhead = !string.IsNullOrWhiteSpace(current)
      && !string.IsNullOrWhiteSpace(latest)
      && !VersionUtil.IsLegacyDate(current) && !VersionUtil.IsLegacyDate(latest)
      && VersionUtil.CompareVersion(current, latest) > 0,
  ```
  ⚠️ **必须挡空串**：`CompareVersion("1.1.4", "")` 会返回 **1**（空侧按 0 补位）→
  不加守卫会把「清单没写版本号」误报成「本机版本更高」。

  - 表头标签 `最新版本` → **`线上最新`**（localAhead 时）
  - `当前 1.1.4 · 最新 1.1.3` → `当前 1.1.4 · 线上最新 1.1.3`

## 八、Skill 市场搜不到 caveman —— 根因与修复路径（老板报障）

老板问：「是不支持联想搜索，还是不能搜到 SkillsMP 全部？」附三图：市场搜 `cave` → 0 结果；
本机工具「完全放行」；SkillsMP 官网搜 `caveman` → 一堆结果。

### 8.1 结论：**都不是「联想」的问题，是数据面只有 615 条**

| 断言 | 证据 |
|---|---|
| 本地搜索**是子串匹配**（`cave` 本可命中 `caveman`） | `static/js/skill-market.js:166-175`：`[title,name,summary,repo,tags].join(' ').toLowerCase().indexOf(q)` |
| 内置清单**只有 615 条 / 218 仓库** | `static/skills-catalog.json` 的 `total=615`；抓取面 = `SKILLSMP_STAR_PAGES=4` + `SKILLSMP_RECENT_PAGES=20`（× 48），再按 `SKILL_PER_REPO_LIMIT=8` 收敛 |
| 615 条里**一条 caveman 都没有** | 全量 JSON 里搜 `cave`/`caveman` = **0 条** → 所以零结果 |
| 「完全放行」**与此无关** | 那是 **Agent 本机工具**权限档；市场刷新由**本地 Python 服务端**发起的 HTTPS，不受它管 |
| 本机**从未成功联网刷新过** | `data/skills_market_cache.json` 与 `data/skills_market_state.json` **都不存在**（后者只在被 429 时写）→ 面板「尚未联网刷新（离线快照 2026-09-21）」正是此意 |

### 8.2 🔑 关键发现：SkillsMP API **支持服务端搜索**，参数名是 `search`

`https://skillsmp.com/api/skills?search=caveman&sortBy=stars&limit=48&page=1`
→ 返回 48 条，含 `JuliusBrussee/caveman` 的 16 个 skill（`caveman`/`-compress`/`-stats`/`-commit`/`-help`/`-review`…）。
实测**其他候选参数全部无效**：`q` / `query` / `keyword` 都返回未过滤的榜单。

其它实测细节（都影响实现）：
- ⚠️ `limit` 硬上限 **48**（`50` → 400 `INVALID_LIMIT`），与项目注释一致。
- ⚠️ **`search` 会同时匹配 name 与 description**：搜 `caveman` 会混进 `orch`/`ultimate`/`sphinx`（描述里提到 caveman）。
- ⚠️ `pagination.total` **不可信**（`totalIsExact: false`：limit=5 时 total=6、limit=3 时 total=7）。
  要翻页只能用 `hasNext`。
- ⚠️ **不传 `search` 时 API 硬封顶 `maxResults=1200`（`isCapped:true`）**，且 `page=26` 会**静默回退到 page 25**（不报错）。
- 🚨 **不传 `search` 的 star 榜是「巨仓霸榜」的**：`page=1` 的 48 条 star 全是 `389030`（同一个巨型仓库），
  `page=5`/`page=12` 全是 `260918`（另一个）。**`stars` 是「仓库 star」而非 skill 自己的** ——
  这就是 `SKILL_PER_REPO_LIMIT=8` 存在的理由。
- ⚠️ `search` **可突破 1200 上限**：搜出来的 `caveman` 覆盖 458~106187 star 的几十个仓库，
  而 1200 条榜单尾部全是 246398 star 的巨仓条目 → caveman 根本不在榜单内。

### 8.3 修复路径（已确认可行，**尚未实施**）

`skillsmp_normalize()` / `skill_market_pace()` 节流闸 / `skill_tags()`）。

## 10. 下午 · Skill 市场面板三处修复 + 重打 1.1.5

老板反馈（截图）：「右上角的筛选功能失去了效果，隐藏多余无用的滑条和黄色文字」。
逐条实测后是**三个独立问题**，全部有实锤（无头 Edge + 临时同源探针量 DOM）。

### 10.1 排序「失去效果」= 并列块太大，不是坏了

- 实测：`hot` / `stars` / `installed` 的前 **14 条完全相同**，`forks` 到第 11 条才变
  → 首屏 7 张卡片一模一样，换排序当然「看不出效果」。
- 根因：**star / fork / 热度都是仓库级指标**，`openclaw/openclaw` 一个仓库 11 条、
  全部 star=389030 / fork=81745 / hot=552520，并列全站第一 → 任何排序都把它们顶在最前。
- 修法：`visible()` 末尾加 **`spreadByRepo()`「同仓错峰」**（同一仓库连续出现不超过 2 条，
  超了往后顺延找别家仓库）。实测 hot↔forks 首个不同位 **14 → 2**。
  ⚠️ 只打散并列块，主排序不变；绝大多数仓库只有 1~2 条，不触上限时与严格排序一致。
- ⚠️ `hot` 与 `stars` 前 10 仍相同 —— 热度 = star + 收藏×2，仓库级 fork/star 比例相近，
  这两个指标本身就高度相关，**不是 bug**。
- 顺带确认：**大分类筛选、子分类筛选本来就正常**（utility→Autoreview…；design→Node Connect…；
  visual→Meme Maker…；other 72 条），别被「筛选失去效果」这句话带偏。

### 10.2 「多余无用的滑条」= 子分类行被压成 0.69px

- 实测 `.asm-tabs` 内容高 **0.6875px**（按钮只剩 padding+border 的 8px，文字全被裁掉），
  24 个芯片全不可见，原位只留一条横向滚动条 —— 就是老板说的「多余无用的滑条」。
- 根因：🚨 **列方向 flex 容器里所有子项默认 `flex-shrink:1`，而 `overflow-x:auto` 会把
  `overflow-y` 也算成 `auto`（CSS 规范如此），滚动容器的 `min-height:auto` 解析为 0** ——
  别的固定行是「内容高度」压不动，只有它被压扁。
- 修法：`.asm-tabs` 改 **`flex-wrap:wrap` 换行铺开** + `flex:0 0 auto`，并去掉 overflow。
  滑条自然消失、芯片全可见（实测 3 行 / 24 芯片 / h=80px）；固定行 +48px，列表仍显示 6 张卡片。

## 11. 傍晚 · Skill 安装失败修复（全站搜索的结果装不上）

### 11.1 现象与根因

老板截图：搜索 `caveman` → 列表 44 条 → 点「安装」→ toast「安装失败：市场清单里没有这个 Skill
（可能已下架，点刷新重试）」。

根因是**两处叠加**，缺一不可：

1. **后端**：`install_market_skill(skill_id)` 只调 `find_market_skill()`，而它只在**联网缓存 +
   内置快照**里找。全站搜索（`/api/skills/search`）的结果**两个都不在** → 必然 404。
   实测内置清单里含 `caveman` 的记录 **0 条**（那 44 条全来自全站搜索）—— 「搜得到却装不上」的真相。
2. **前端**：`AgentSkillRequest` 只有 `id` 字段，安装时 `JSON.stringify({id})` —— 后端拿不到
   `raw_url` 等任何信息，**想兜底也无从下手**。

### 11.2 修法

- **后端**：`AgentSkillRequest` 加 `raw_url` / `name` / `title` / `summary` / `repo`（均可选）；
  `install_market_skill(skill_id, hint=None)` —— **内置清单优先，找不到才用 hint**（服务端自己抓的
  地址更可信）；新增 `skill_raw_url_ok()` 白名单（**只允许 `raw.githubusercontent.com`**）防 SSRF ——
  hint 里的 URL 会让本机去 GET，不校验等于开放任意 URL 请求。实测内置 827 条的 raw_url **全部**
  是 raw.githubusercontent.com，白名单有据可依。
- **前端**：新增 `recordById()` —— 🚨 **必须同时查 `state.skills` 与 `state.remote`**，
  全站搜索结果只活在后者里（`skillById()` 只查前者，所以拿不到 raw_url）；`install()` 把整条记录
  一起 POST。

### 11.3 验证（三层，全程不碰老板的数据）

1. **函数级（隔离）**：monkeypatch `agent_skill_dir` 到临时目录 + `save_installed_skills` 空操作
   → 用 hint 真实下载安装成功（14432 bytes 落盘）；无 hint 仍 404；恶意 URL 被 400 拒。
2. **路由级**：`fastapi.testclient.TestClient(m.app)` + 同样隔离 → 200 / 400 / 404 三种语义全对
   （证明 Pydantic 新字段真能解析，不只是函数签名对）。
3. **前端**：无头 + 3011 临时实例，探针搜 `caveman` 后读 `SkillMarket.state` →
   `R=44 URL=44 LOCAL=false` —— 44 条结果**全部带 raw_url**、且**本机清单里没有**，
   两个前提同时成立。

## 12. 傍晚 · 「联网搜索又失效」= 限流时**空数组被误判**（前端 bug）

### 12.1 现象

老板截图：搜 `caveman` → 列表空白、分类计数全 0、中间大字「SkillsMP 全站也没有匹配的
Skill」，meta 行两条橙字「SkillsMP 限流冷却中（约 5 分钟后可再试）…」。

### 12.2 根因：`!!state.remote` 对**空数组**是 true

限流时后端**仍返回 HTTP 200**，只是 `skills = []` + `note = "限流冷却中…"`。
前端 `remoteActive()` 原实现 = `q >= MIN && !!state.remote && remoteQuery === q` ——
**空数组是 truthy** → 被误判成「正在展示全站结果」。两个后果都很难查：

1. `currentSource()` / `visible()` 拿到空数组 → **不再回落本机清单** → 列表一片空白，
   哪怕本机清单里明明有匹配 —— **这才是老板说「搜索失效」的真正观感**；
2. 空态文案走 `asmEmptyOnline` → 说成「SkillsMP 全站也没有匹配的 Skill」，
   而实际**根本没搜成**（caveman 全站有 44 条）。

### 12.3 修法

拆成两个判据（`static/js/skill-market.js`）：

- `remoteSearched()` = `q >= MIN && Array.isArray(state.remote) && remoteQuery === q && !state.remoteNote`
  —— **真的联网搜成功**（哪怕 0 条）；
- `remoteActive()` = `remoteSearched() && state.remote.length > 0` —— **搜成功且真有结果**，
  空结果必须回落本机清单。
- meta 行的「命中 N 个」与空态文案都改用 `remoteSearched()`：「命中 0 个」是有用信息，
  只有限流/失败才不该报命中数。

### 12.4 验证（无头 + **拦截 fetch 假装限流**，不消耗真实配额）

| 场景 | 修复前 | 修复后 |
|---|---|---|
| 搜本机**有**的词（docx）+ 限流 | 卡片 0（空白） | **卡片 7**（正常回落本机） |
| 搜本机**没有**的词（caveman）+ 限流 | 「全站也没有匹配的」 | 「没有匹配的 Skill」（如实） |

### 12.5 ⚠️ 教训：别在老板使用期间起第二个实例做**联网**测试

- 冷却状态**持久化在 `data/skills_market_state.json`**（`mark_skills_market_cooldown()` 落盘），
  但**节流闸 `skill_market_pace()` 是进程内的** —— 我起的 3011 实例与老板的 3000 实例
  **各自独立计时、却共享同一个上游 IP 配额** → 两进程交替请求时实际间隔可能 < 1.2s，**加剧限流**。
- 更省的做法：验证限流行为**拦截 fetch 假装限流**即可，不必真打上游。
- 另：老板截图里「本次沿用现有清单」说明他点过**刷新**，而刷新要抓 **24 页**（≈29s），
  是限流的主要来源；刷新与搜索**共享同一冷却状态**（`SKILL_MARKET_COOLDOWN`，有意的保护，别改）。
- 提交 `a4beafb`；更新说明新增第 6 条（type=`fix`，`safe_update_notes` 对 type 无白名单限制）。
