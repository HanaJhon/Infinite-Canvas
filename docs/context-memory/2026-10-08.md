## 1. 调研：本项目 `smart-3d` 的处理流程 vs `img2threejs/img2threejs`

老板问：「该项目中的 three.js 功能处理流程是否与 img2threejs 相同」→ **不同，本质是两种东西。**

### 1.1 本项目 `smart-3d` 的完整链路（带代码位置）

1. 节点创建 `static/js/smart-canvas.js:6935` `type:'smart-3d'`；上游**只接「上传」节点**（见 MEMORY §四）。
2. 点运行 → `run3DNode()`（`:9813`）：无上游 / 无图 / 无视觉模型 → toast 拦下。
3. 前端 `POST /api/canvas-llm`（后端 `main.py:20247`，通用 LLM 转发，**单次调用、无重试、无多轮**），带：
   - `message` = i18n `smart.3dRunPrompt`（`:462`）
   - `images` = 上游图片 URL
   - `model`/`provider` = 节点上选的**对话视觉模型**（`chat_models`）
   - `system_prompt` = `SMART_3D_SYSTEM_PROMPT`（`smart-canvas.js:9095`，**硬编码**）
4. **要求模型返回一个 JSON**：`{camera:{position,target,fov}, objects:[{name,type,size|radius|…,position,rotation}]}`
   - 白名单 7 种 primitive：`box / sphere / cylinder / cone / torus / capsule / plane`
   - 约束：4~24 个 primitive、单位约米、整体限制在 4×4×4 盒内、底部贴 `y=0`
   - 🚨 **明确禁止输出颜色 / 材质 / 灯光 / 地面 / 背景**（提示词里写死 "Geometry only"）
5. 解析：`smart3DParseSceneJson()`（`:9123`，去 markdown fence / 取首尾大括号 / 修尾随逗号）→ `normalize3DScene()`（`:9150`，**仅数据清洗与数值兜底，无任何质量门**）。
6. 渲染：`node.scene3d` + 内嵌 `static/vendor/js/three-0.160.0.module.js`（unpkg 镜像，见 `static/vendor/MANIFEST.md`）
   - `SMART_3D_STUDIO`（`:9259`）：纯白背景 + 浅灰黏土 `#d9dce1`（roughness 0.62）+ key/fill/rim 三灯 + 半球光 + `ShadowMaterial` 地面
   - `build3DStudioEnvironment()`（`:9274`）：手搭 14³ 房间 + 3 块纯白柔光板 → `PMREMGenerator` 卷积
   - `smart3DGeometryFor()`（`:9305`）spec → BufferGeometry；`smart3DOrbitFromCamera()`（`:9331`）用 LLM 给的 camera 参数
   - 节点 UI 可调 FOV 20–90（`:9742`），模型/通道下拉走 `chatModelOptions()`（MEMORY §三）
7. 收尾 `upload3DSnapshot()` 截图存节点。

→ **本质：一次性 LLM 出 primitive 列表 → 统一黏土材质预览**，轻量「识别 + 示意预览器」。

### 1.2 `img2threejs`（17.7k★，Apache-2.0，v2.0.0，Python，2026-07 创建）

- 定位：**Claude Code / Codex / OpenCode 的 Skill**（装到 `~/.claude/skills/`），**不是应用内功能**。
- 输入一张参考图 → 输出 **TypeScript 的 `THREE.Group` 工厂代码**（真代码，非 JSON spec）。
- 分阶段雕塑管线：`blockout → structural → form → material → surface → lighting → interaction → optimization`，**每个 pass 生成后视觉模型 review → 自纠正 → 过阈值才进下一个 pass**。
- 生成前先做 **detail-first 分析**（`detailInventory`：光泽/倒角/螺丝/刻线/轮廓/污渍磨损），**严格质量门阻止生成直到清单完整**。
- subject 分类 `object` / `character` / `hybrid` 走不同轨道（character 有 anatomy-aware 轨道：head-unit 比例、面部地标、姿态）。
- 输出含**运行时层级**（pivots / sockets / colliders，animation-ready）与完整材质（版本化 Three.js 材质注册表 + per-region 对比门）。
- 确定性 Python 脚本（`forge/state.py` 断点续跑、`forge/next.py`）做校验/门控；**浏览器 Three.js 仍是渲染权威**，Python 只做编排与诊断。
- 可选高级路径：likeness maximization（投影优先）、multi-view silhouette carving（`geometryDescriptor.visualHull` 体素求交）、CS2 武器 domain 审核门。
- 插件体系：`img2` harness + plugin-cs2 / plugin-character / plugin-img2glb / plugin-hello-cube。

### 1.3 唯一相似处

都在做 **image → three.js 的「按代码 / 参数重建」**（都明确不走 photogrammetry、mesh 提取、下载模型资产），最终都由浏览器 three.js 渲染。

### 1.4 结论与可借鉴点

**流程不同。** 本项目 = 单次 LLM + 7 primitive + 固定黏土材质的轻量预览；img2threejs = 多 pass 迭代 + 视觉质量门 + 输出可动画 TS 代码的重建管线。

若要把 `smart-3d` 往那个方向推，最值得借的**不是它的规模**，而是三件小事：
1. **细节清单（detailInventory）先于生成** —— 当前提示词只给了 primitive 约束，没要求先枚举身份定义细节；
2. **每轮出图后自检再重试** —— 当前一次性，模型返回不合法 JSON 就 `scene3dError` 报错，无自纠正；
3. **几何与材质分离** —— 当前禁止模型输出材质是**有意为之**（统一预览观感）；要改需先决定产品定位是「保真重建」还是「结构示意」。

## 2. `smart-3d` 改造：从「一次生成」改为「细节清单 → 分阶段 → 每轮视觉自检」

老板要求：把 3D 节点的流程改成 img2threejs 那套（细节清单 + 质量门 + 多轮迭代），但 ① 参考图入口保持原来的**「上传」节点**；② 最终**视觉呈现不变**（仍在 three.js 节点里）；③ 节点的**交互视觉**按新流程改造。

### 2.1 关键设计决策（已与老板确认）
- **阶段划分：4 个几何向维度** —— 大形 `blockout` / 结构 `structural` / 形体 `form` / 轮廓 `silhouette`。
  裁掉 img2threejs 的 material / surface / lighting：本节点禁止模型输出颜色，那三段没有意义。
- **迭代强度：默认 3 轮 + 保留快速模式开关**，约 7 次多模态调用（1 清单 + 3 生成 + 3 自检）。
- 🚨 **编排放前端（不是后端）**：视觉自检要「渲染后截图再喂回模型」，而渲染在浏览器里，后端拿不到画面。
  复用现有 `/api/canvas-llm`（多模态）+ `/api/ai/upload-base64`（截图转 URL），**后端零改动**。

### 2.2 实现（`static/js/smart-canvas.js`）

## 3. 排查「3D 节点报 `404 page not found`」（老板截图 12:16）

**结论：不是 3D 节点代码的问题，是当时生效的 Grsai 平台配置把 chat 地址拼错了；老板 12:17 自己保存配置后已恢复。**

**时间线**（全部来自 `output/server-3010.log` 行 205–255）：
1. `[canvas-llm] model=gpt-6-astra provider=grsai text_len=45 images=1/1` → `POST /api/canvas-llm` **404**（连续 3 次）。
   `text_len=45` 正是 `smart.3dIntakePrompt` 的长度 → 卡在**细节清单的第一次调用**，所以节点显示「已识别 0 个对象」。
2. 老板进 API 设置：`POST /api/providers/probe-async` 200、`POST /api/providers/test-connection` 200（都是**应用层 200**，见下）。
3. **`PUT /api/providers` 200** ← 保存 Grsai 配置。
4. 同一条调用立刻 **200**；随后 `text_len=40`（生成轮次 = `smart.3dRunPrompt` 长度）、
   `text_len=41 images=2/2`（自检 = `smart.3dReviewPrompt` 长度，2 张图 = 参考图 + 渲染截图）全部 200，
   并出现 `POST /api/ai/upload-base64` 200（截图回传）与 `GET /static/vendor/js/three-0.160.0.module.js` 200。
   → **新迭代流程其实已经完整跑通**；老板截图那一刻（12:16:30）是修好（12:17）之前的状态。

**根因**：`resolve_chat_provider()`（`main.py:4642`）拼 chat 地址的规则是「`base_url` 不以 `/v1` 结尾就补 `/v1`」，
再接 `/chat/completions`。`base_url` 只要带路径后缀（例如照文档抄成 `https://grsai.dakka.com.cn/v1/api`）就会拼成
`.../v1/api/v1/chat/completions` → Grsai 的 Go 网关对不存在的路径统一回 `404 page not found`。
⚠️ **拼不出旧值**：`data/api_providers.json` **未纳入 git、也没有任何备份**。

**两条实测确认的坑**：
- **「测试连接」按钮对 Grsai 恒报失败**：它调上游 `/v1/models`，而 Grsai 该端点本身就返回 `404 page not found`；
  `test_provider_connection`（`main.py:17343`）把失败包成 **HTTP 200 + `{ok:false}`** → 日志里的 200 不代表连通。
- **两个环境的平台配置是两份**：安装目录那份 Grsai 是 `id=ep_1790048388395` / `protocol=grsai`，
  工作区这份是 `id=grsai` / `protocol=openai`。**在 3010 上改的配置不会同步到安装目录。**

**回归验证（全 200）**：直连 `POST /v1/chat/completions` 纯文本 → `pong`；1×1 图 → `Pale yellow`；
老板那张真图（1.18 MB PNG → data URL 1.57 MB）→ `Three objects.`；经 `/api/canvas-llm` + 真实参考图路径 → 正常返回 JSON。

**顺带查明**：Grsai **不是**后端内置平台（`default_api_providers()` 里没有 `"id": "grsai"`），是用户自建的。

## 6. 「处理前和处理后都是黄色吗」—— 两个发现（老板截图 13:36）

**回答**：不是同一种态。未评=灰底圆点（不显示分数）、已评未达标=黄底+分数、已评达标=绿底+分数。
老板截图里四枚**都是黄底+分数**，说明四维**都已有评分记录**。

### 6.1 「处理前」也黄的原因（设计副作用，非 bug）
四维评分持久化在画布上（`node.smart3d.dims`，`smart3DFreshState` 有意保留 → 刷新后仍能看到上次结论）。
所以点「重新生成」**之前**看到的就是**上一轮留下的分数**；跑完再刷新分数，还是黄的 → 看起来「处理前=处理后」。
→ 可改：运行时把 `dims` 清空回到未评态、旧分数挪进 title，跑完逐轮填分。

### 6.2 🚨 两个节点其实都跑挂了，但**界面上完全看不见**
`node.smart3d.stage` 实测都是 **`'error'`**（`:10166` catch 里写入），日志对应：
- `3d_7l1i7l3vu44l`：自检调用（`text_len=41 images=2/2`）后 → **`POST /api/canvas-llm` 502 Bad Gateway**（log 行 121）
- `3d_f3idauxu90v7`：生成调用（`text_len=40 images=1/1`）→ **400 Bad Request**（log 行 125）

**是上游（Grsai）抖动，不是我们的代码**：同样的 `text_len=40` 生成请求在行 85/91/116 都成功过。
🚨 **失败不可见的根因**：`smart3DBodyHtml`（`:9999`）里错误占位**只在 `objects.length === 0` 时渲染**
（`objects.length ? '' : placeholder`）→ 节点里已经有渲染结果时，`scene3dError` 完全不显示，只剩 toast 一闪。
→ 可改：有渲染结果时也在节点上留一行红字错误。

### 6.3 另一处遗留（我引入的）
`state.focused` 我放进了 `smart3DFreshState` 的保留列表 → **跨运行累积**（实测节点1 是 `['blockout','structural']`）。

### 关键事实（实测，别再踩）
1. **Photopea 可嵌入**：`photopea.com` 无 `X-Frame-Options`、无 CSP、`access-control-allow-origin: *`。
   iframe 指向外部站点 → **必须联网**。跨域读不到本地图片 → 图层 PNG 一律走
   **data URI + `app.open(uri, null, true)`**（照官方 `addImageAndWait` 轮询 `layers.length`）。
2. **`doc.layers[0]` 是最上层** → 按 z **从小到大**注入，堆放顺序天然与原图一致。
3. **图像模型会改变输出尺寸**（1200×1500 → 1254×1254）→ 必须「按 bbox 裁切 → 补正方形 → 重绘 → 缩放贴回原位」；
   元素层一律产出**全画布尺寸**，位置天然对齐（**这是元素层位置精确的原因**）。
4. 🚨 **后端喂图缩到长边 1024**（`media_reference_to_url` → `reference_to_data_url`）→ 模型回报的
   **bbox 与 font_size 都是缩放后坐标，两者都必须按 `sx,sy` 还原**。font_size 一度漏还原 → 文字小 32%（已修）。
5. **`reference_to_data_url` 只缩不放**，且缩放时**强制转 JPEG + 合成白底（丢 alpha）**。
   想让模型看清小目标必须**自己先 resize 放大**。
6. **模型 bbox 不精确**：整图提问时文字框偏 ~41px / 大 1.9×（1200×1500 图）。
   → 加 `split_refine_text`：裁局部 + 自放大 2–3× 再问一次。实测偏差 **41px → 19px**。
7. 🚨 **模型对 font_size 的估计不可靠且不随放大倍数缩放**：整图问给 16（换算后 23）、放大 2× 问给 28（换算后 14），
   而按原图墨迹行长度反推应为 **23**。→ **字号只认整图那次（缩放后），精修只改位置框，不覆盖 font_size**。
8. **原图 logo 字体比 Arial 窄得多**（墨迹 29×78，aspect 0.372；Arial Bold 只有 0.218）→ 字号不可能两头都对。
   **选择匹配「行长度」**（避免溢出）：Arial Bold 下 `行长度 ≈ 字数 × 0.68 × 字号`。
9. **本地白底去背兜底** `split_local_cutout`（四边 flood-fill）：1.8 秒、产品图效果极好、**零新依赖**（只用 PIL）。
