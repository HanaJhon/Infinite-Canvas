### ① 修掉 `read_text_attachment` 重名（真缺陷，比预想严重）

**问题**：同名函数定义了两次，Python 后定义覆盖前定义 ⇒ L6023 那份**静默失效**。

| 版本 | 行为 | 默认上限 |
|---|---|---|
| L6023（Agent 侧） | 纯文本 UTF-8→GBK；**二进制返回 `None`** | `AGENT_FILE_INLINE_CHARS`(20000) |
| L12009（chat 侧） | 支持 xlsx/docx；**失败返回 `""`** | `MAX_ATTACHMENT_TEXT_CHARS`(12000) |

**实际影响（比"死代码"严重得多）**：
- 两个扩展名集合差 **32 种**：`AGENT_FILE_TEXT_EXTS` 有 50+ 种，`TEXT_ATTACHMENT_EXTS` 只有 16 种。
- Agent 独有但 chat 没有的：`.tsv .jsonl .ini .toml .srt .vtt .sql .pyw .mjs .cjs .scss .less .htm .vue
  .svelte .java .kt .c .h .cpp .hpp .cs .go .rs .rb .php .sh .env .properties .conf .cfg`
  ⇒ **用户给 Agent 传 `.go/.java/.sh/.toml` 等代码文件，Agent 读到的是空串。**
- 且 `extract_attachment_text` 的「`None` = 抽不出来」契约**永远不成立** ⇒
  `agent_files_context_block` 的 `if text is None:` 降级分支（"请用 read_file 自行查看"）**永远走不到**，
  只会注入一个空代码块。

**修法**：把 Agent 那版**改名**为 `read_agent_text_attachment`（并在 docstring 里写明为什么必须两个名字），
`extract_attachment_text` 改调它。chat 侧 `read_text_attachment` 原样不动。

**实测验证**：
```
agent .go 文本      -> 'package main\r\nfunc main(){}\r\n'   （修复前是 ''）
agent .go 二进制    -> None                                  （契约恢复）
extract .go 二进制  -> None                                  （会走降级提示）
chat  read_text .go -> ''                                    （chat 侧行为不变）
chat  read_text .txt-> 'hello'
```
