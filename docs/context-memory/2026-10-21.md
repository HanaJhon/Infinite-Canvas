## §1 「思考模式为什么还是直接失败」——尺寸护栏 + 失败要给出路（老板截图）

老板截图：需求「将画面中的画布风格换成浅色风格」，参考图 4096×4096，Agent 出了 plan + prompt，
然后一张红字：`GPT-Image-2 不支持当前尺寸 4096x4096…`。老板问：**开启了思考模式，为什么还是缺乏
应变能力？遇到问题找不到解决方案时，不是应该问用户要方案，而不是直接失败？**

### 一、根因（三条，都不是「模型笨」）
1. **4096×4096 是必然失败**：agent 默认 `genResolution='4k'`，方图 `SIZE_MAP.square['4k']='4096x4096'`
   = 1677 万像素，而 GPT-Image-2 上限 829 万（长边 3840）⇒ **超一倍**。
2. **后端早就会缩，但画布这条路没调**：`normalize_gpt_image_2_size()`（4096²→2880²）一直存在，
   但只被 L8994「在线生图参数默认值」用过；`create_canvas_image_task` 一次都没调。
   注释还写着「不对尺寸做任何缩小（用户选什么就原样发送）」—— 于是确定性的失败被当成正常请求发出去。
3. **失败后链路把控制权交给了 DOM**：`gen.error` 只是一行红字，**模型根本没参与善后**
   （它连「失败了」都不知道，下一轮历史里只看到自己写的 prompt）。所以它不可能应变。

### 二、改了四处
- **前端尺寸护栏 `agentGuardGenSize(size, model)`**（`apiImageSize` 之后）+ `runAgentGenerations` 出图前调用：
  超限就等比压到 ≤3840/≤829万（16 对齐），**只对已知上限的模型动手**（nano-banana 的 4K 不压），
  压过就写 `gen.sizeNote`，卡片上显示「已自动按 2880×2880 生成」——**不许静默改**。
- **后端 `guard_size_for_model(model, size)`**（`gpt_image_2_size_exceeds_supported` 之后）+
  `create_canvas_image_task` 入口调用，task 里回 `size_requested / size_used / size_note`，
  POST 响应也带上。算法与前端**必须一致**（2880×2880）。
- **编排上下文补事实**：`agentOrchestrationContext()` 的【可用生图能力】给每个 gpt-image-2 模型标
  「长边≤3840、≤829万像素，4K 方图 4096×4096 会被拒」。🚨 又是那条铁律：**只给规则不给事实 = 模型只能瞎猜**。
- **思考模式系统提示词**（`agentSystemPrompt` 的「第二步 · 定能力」）加两条：
  ① **发出去之前自检三件事**（尺寸吃不吃得下 / 参考图数量 / 局部重绘目标是否唯一），能改就当场改；
  ② **改不了就开口问**：说清卡在哪 + 在 `options` 里给 2-3 个能直接选的方案，别硬做也别直接失败。
- **失败卡片给出口**：`[data-agent-ask-fix]`「让 Agent 想办法」→ 把失败原因 + 原始需求带回输入框
  （**只填不发**，避免每次失败偷偷烧一次 LLM），点发送后模型给方案（走它自己的 options 通道）。

### 三、验证
- 后端单测 8 例：4096²→2880²（正好 829 万，不超）、2352×3520/3840×2160/2160×3840/2048² 原样、
  auto 原样、nano-banana 的 4096 不动、5120×2880→3840×2160。
- 后端接口实测（bogus provider 不花钱）：`size_used` 分别回 2880x2880 / 2048x2048 / 4096x4096。
- 前端 `__sizeguard_test.js` **23/23 PASS / pageErrors 0**（含卡片显示尺寸说明、失败卡片只有一个出口按钮、
  点按钮不自动发送、输入框含失败原因+原始需求+「给两三个可选方案」、系统提示词含自检三件事与「开口问」）。
- 回归 `__editmsg_test.js` **28/28 PASS**（重编辑历史对话没被破坏）。
- 服务已重启：`?v=1.2.1.1792546060`（js）/ `1.2.1.1792545819`（css）。

### 四、没做的事（说明取舍）
- **没有「失败后自动让 LLM 重新规划」**：每次失败都多一轮 LLM（Grsai 慢到 2-4 分钟）+ 花钱，
  所以做成「用户点一下才问」。尺寸这类确定性错误直接自动修，**问了反而是骚扰**。

### 二、§1 的错在哪
- 我把 1:1 的 2880×2880 当成「4096 超限后压出来的」，其实**它就是 4K 档本身**。
  结论一样（都是 2880），但**过程错**会导致文案说错话：报错里写「GPT-Image-2 不支持 4096」，
  老板看到的是自己选的 sunburst，以为系统认错了模型。
- 更实质的问题：**套通用 `SIZE_MAP` + 等比缩，会算出非官方尺寸** ——
  3:2 的 4K 会得 3520×2352（官方 3504×2336）、4:3 的 2K 会得 2048×1536（官方 2304×1728）、
  4:3 的 1K 会得 1344×1008（官方 1152×864）。能出图，但不是官方档位。

### 三、改法
- 前端新增 `GPT_IMAGE_FAMILY_SIZES`（15 个比例 × 最多 3 档）+ `gptImageFamilySize(ratioKey, resolution)`；
  `runAgentGenerations` 里**先查官方表**，命中就用；查不到（普通模型）再走 `apiImageSize` + 护栏。
  `1:3`/`3:1` 官方只有两档 → 取 index 时 clamp 到最后一档。
- 官方表命中时若「4K 但长边 < 3840」（1:1/4:3/3:2/5:4…），卡片上必须解释一次
  「XX 的 4K 规格就是 2880×2880（该系列按总像素约 829 万封顶）」—— 否则老板会以为偷偷降了画质。
- 后端 `gpt_image_2_size_error_message(size, model="")` 与 `guard_size_for_model` 的 note
  **改为写真实模型名**；报错文案里补上「1:1 的 4K 是 2880×2880、16:9 的 4K 是 3840×2160，按官方档位选就不会被拒」。
- 编排上下文改口径：以前写「4K 方图 4096×4096 会被拒」→ 会让模型**不敢填 4k**。
  现在写「4K 档 1:1=2880×2880 … **直接填 resolution="4k" 就行**，别自己换算成 4096」。

### 四、验证
- `__famsize_test.js` **29/29 PASS / pageErrors 0**，含**端到端**（拦 `fetch` 看真实 payload）：
  sunburst 1:1+4K 实发 `2880x2880`、3:2+4K 实发 `3504x2336`、Grsai 的 nano-banana 1:1+4K 仍 `4096x4096` 且不加说明。
  另有「全表 15 比例所有档位都不超 3840/829 万」「官方尺寸全部不会被护栏二次压缩」。

## 三、纯提问被当成生图需求（老板问「为何正常对话也出现生图流程」）

### 一、现象
问「该版本是采用了遮罩局部重绘还是整张图的图生图？」→ 助手**正确回答**了，但下面又冒出
一张「**生成失败·整图重绘**」红卡，卡片 prompt 就是这句问话，报错「上游内容审核拒绝」，
再往下还有一条「提示词确认 · 1已确认 / #1 该版本是采用了…」，等于**问话被当成提示词发出去了**。

### 二、根因（两处叠加，都是「关键词/子串」判据）
1. `looksLikeGenRequest()` 的关键词表里有 **`张图`** ⇒ 「整**张图**的」命中 ⇒ 判成生图需求。
2. 思维模式兜底（`processAgentLlmResult` 里 `else if(looksLikeGenRequest(text) && !isModifyRequest)`）
   在「模型没给结构化结果 + 判定为生图需求」时，用 `prompt: text` **原样造一条待确认提示词**
   ⇒ 弹确认卡；老板点了确认 → `runAgentGenerations` 把问话发出去 → 审核拒绝。

### 三、改法（三层，先语义后关键词）
- 新增 `isQuestionOnly(text)`（紧邻 `looksLikeGenRequest`）：
  `AGENT_ASK_VERB_RE`（帮我/给我/请你/来一张/把…改成/用这张图重绘）**命中就是需求**；
  否则再看 `AGENT_ASK_MARK_RE`（结尾 ？/还是/是否/为什么/怎么/如何/哪一张/区别…）。
- `looksLikeGenRequest` 开头加 `if(isQuestionOnly(t)) return false;` —— **没动 `张图` 关键词**，
  因为「这张图改成浅色」「整张图重绘成浅色」还要靠它命中；收窄它会把真需求一起漏掉（实测过）。
- 非思维模式兜底：`hasAnyIntent && !isQuestionOnly(userText)`（模型爱写「要为您生成…吗？」）。
- 兜底第二层（`const assistantMsg` 之前）：`isQuestionOnly` 时，把 **prompt ≈ 用户原话** 的
  prompts/generations 过滤掉（归一化去标点后相等，或原文包含且长度≥8）。**只丢回声，模型改写过的保留**。

### 四、踩到的坑
- 首轮 `AGENT_ASK_VERB_RE` 写了 `用.{0,12}(重绘|重画|生成|改)` ⇒「采**用了遮罩局部重绘**」命中
  ⇒ 问句仍被当需求（测试 2 例红）。改成 `用(?:这|那|原|参考|此)张?图.{0,10}(重绘|重画|修|改)`
  —— **「用」后面必须跟图**才算动作。
- 同一根因还连带一个副作用：问句被判成生图需求后，`_wantsInpaint`（含「局部重绘」）
  让「没遮罩不许出图」那道闸也跳了，把好的 reply 覆盖成「「目标」节点上还没有遮罩」。

### 五、验证
- `__askguard_test.js` **9/9 PASS / pageErrors 0**：5 个问句全拦、6 个真需求全放（含「怎么把这张图改成蓝色？」）、
  端到端「模型什么都没给」→ 0 prompts/0 gens、端到端「模型吐回声 generation」→ 被过滤、对照组真需求保留、
  全程 0 次网络请求。
- 回归：`__sizeguard_test.js` 23/23、`__editmsg_test.js` 28/28、`__famsize_test.js` 29/29。
- 服务重启后 `?v=1.2.1.1792549035`（== js mtime）。
- 测试脚本已归档 `output/_tmp-cleanup-20261021/`；临时画布全部 purge。

## 六、空回复被当成正常回复 → 5 张垃圾图（老板问「底层是否被替换了」）

### 现象
用户消息带 `[文件:图需-后排.xlsx]` + `[图:主图.jpg]`，说「生成附图1-5，5张图同时生成」。
助手回一句**「接口返回了空回复。」**，紧接着冒出 **5 张**「正在生成图片…」的卡，
prompt 全是**用户原话**（连 `[文件:]`/`[图:]` 标记一起），只加了「变体2/3/4/5」后缀。

### 根因（不是底层被替换，是「空」被当成了内容）
1. 后端 `canvas_llm` / `canvas_llm_stream`：上游 200 但正文空 → `text or "接口返回了空回复。"`，
   **仍然 status=succeeded** 返给前端。
2. 前端 `processAgentLlmResult` 把它当正常 reply → 不是 JSON → `parsed.reply` = 这句占位文案 →
   `looksLikeGenRequest` 命中（含「生成/张图」）→ 思维模式兜底 `prompt: text`（**用户原话**）→
   `requestedCount=5` 的「补齐到 N 条」再复制出 5 条带变体后缀的 prompt → 5 次真实生图请求。

### 修法
- **后端**（`main.py`）：
  - 新增 `EMPTY_LLM_REPLY` / `describe_empty_llm_output(finish_reason, saw_reasoning)` /
    `friendly_empty_llm_error(reason, model)`。病因四档：`length`（token 全花在思考上被截断）/
    `content_filter` / 只有 `reasoning_content` / 单纯空正文。
  - `canvas_llm_stream` 逐块记 `finish_reason` 与是否出现 `delta.reasoning_content`；
    `canvas_llm` 从 `choices[0].finish_reason` + `message.reasoning_content` 判；两者都在空时返回 `empty_reason`。
  - `run_agent_llm_task`：结果 text 为空或等于占位文案 ⇒ **直接 raise → status=failed**，
    `result` 不写入。错误文案指名模型 + 建议换非思考型模型 / 拆小任务 / 检查模型名。
- **前端**（`smart-canvas.js`）：
  - `processAgentLlmResult` 开头早退：空回复只 push 一条 `intent:'error'` 的说明，**0 prompt / 0 generation**。
  - 新增 `agentPromptFromUserText()`：兜底 prompt 洗掉 `[图:|文件:|节点:]` 标记；洗空就不造 prompt
    （两处兜底都改：非思维 `finalPrompt`、思维模式 `parsed.prompts`）。

### 验证
- 前端 `__emptyreply_test.js` **11/11 PASS**（占位文案/空串都不出图、runAgentGenerations 0 次、兜底洗标记、真需求仍能兜底）。
- 后端 `__empty_backend_test.py` **12/12 PASS**（4 档病因、文案关键词、空→failed 且 result 为 None、正常→succeeded）。
- 回归：askguard 9/9、dock 15/15、sizeguard 23/23、editmsg 28/28、famsize 29/29。
- ⚠️ **没法在本机复现「空回复」本身**：这台机器的服务进程连不到外网（direct/proxy 都 000），
  说明老板那次请求确实到了上游并拿到 200，只是正文空。下次再犯，新文案会直接写 `finish_reason`。

## 七、选了 sunburst 却用 flare —— 同通道型号被模型顶掉

老板原话：**「我选的模型明显不是gpt-image-2.5-flare，而是gpt-image-2.5-sunburst」**。
截图三处证据：尺寸说明、红色错误卡、以及「⚠️ 两个文件均未上传到画布」那行上方的卡片，
写的全是 `gpt-image-2.5-flare`；而通道下拉里选的是 `sunburst`（通道已换成 Aizzz-image）。

### 根因（不是通道配错，是「模型可以偷偷改型号」）
`normalizePrompts()` 原来这么写：
```js
if(wantModel && (prov.image_models || []).includes(wantModel)) normalized.model = wantModel;
```
模型在【可用生图能力】清单里看得见同族所有型号（flare / sunburst / gpt-image-2.5…），

### 根因（跟 §三「纯提问」是同一个病）
1. `looksLikeGenRequest` 的关键词里含 **`张图`** ⇒「描述这**张图**」直接命中，被判成生图需求。

3. 渲染层（`agentMessageHtml`）的条件就是 `msg.prompts.length > 0` ⇒ 有 prompts 就出卡。

## 十、Agent 读不了 Excel —— 真凶是「工具结果回灌被砍到 4000 字符」

### 先说清事实：面板一直是「开」的，但停在**收起态**
实测 `#agentPanel` 是 `opacity:1; visibility:visible; display:flex`，`open` 类也在 ——
问题出在 `chatDrawerOpen`：`loadAgentState()` 里的默认逻辑是
**「有历史消息才展开，一条都没有就收起」**，所以新画布 / 刚清过上下文时只剩一颗胶囊（h=0）。
老板看不到对话区，就以为功能被关了。

### 改法
```js
if(typeof agentState.chatDrawerOpen !== 'boolean' || !agentState._dockDefaultExpanded){
    agentState.chatDrawerOpen = true;
    agentState._dockDefaultExpanded = true;
}
```
- 默认展开；
- 🚨 **必须做一次性迁移**：老板 localStorage 里很可能已经存着 `chatDrawerOpen:false`，
  只改默认值救不了老数据（`typeof` 已经是 `boolean`，走不进原来那个分支）。
  用 `_dockDefaultExpanded` 打标记，**只强开一次** —— 之后他手动收起仍然记得住，不会每次刷新都对着干。

  | 全新画布（无状态） | 展开 h=446、对话区可见、胶囊「收起对话」 |
  | 老状态存着 false、无迁移标记 | **迁移后展开** ✓ |
  | 用户已主动收起（有标记） | **保持收起** ✓（尊重手动操作） |
- 回归：dock 15/15、ui4 14/14、inspire_clear 7/7、nogencard 17/17、askguard 9/9、

### 追加：有正在运行的对话时自动展开

老板原话：**「当有正在运行的对话时，自动展开」**。
收起态只剩一颗胶囊，消息发出去了、图在生成，用户却看不到任何进度和产出。

实现只改**一处** —— `renderAgentMessages()` 开头（渲染是所有运行入口的公共必经之路，
不用去 5 个 `agentSending = true` 各写一遍）：

```js
if(!agentState.chatDrawerOpen){
    const _running = agentSending || agentThinking
        || (agentState.messages || []).some(m => (m.generations || []).some(g => g && g.status === 'running'));
    if(_running){ agentState.chatDrawerOpen = true; applyAgentDockSize(); saveAgentState(); }
}
```

- 🚨 **判定不能只看 `agentSending`**：刷新页面恢复的图生任务、从快捷操作触发的变体，
  `agentSending` 可能是 false，但 `generations` 里仍有 `status === 'running'`。
- ⚠️ **只在跑起来时展开，跑完不自动收起** —— 结果还留在那儿，收起是用户自己的决定。
- ⚠️ `applyAgentDockSize()` 不回调 `renderAgentMessages`，不会递归。
- 只在「收起→展开」这一刻写一次 `saveAgentState()`（内部有 200ms 防抖）。

验证 `__agent_autorun_test.js` **9/9 PASS**：agentSending 展开 / running 生图展开 /
没运行保持收起 / 跑完不收起 / 用户收起后不被渲染弹回来 / 下次运行再展开。

## 十三、小抽AI 窗口可拖拽移动 + 四角缩放

老板原话：**「允许拖拽来移动小抽AI窗口，允许拉动窗口四个角来调节窗口大小」**。

### 实现
- **HTML**：`.agent-panel` 末尾加 4 个 `<div class="agent-resize-handle nw|ne|sw|se" data-agent-resize="...">`。
- **CSS**：默认仍是「底部居中」；一旦拖过就加 `.dragged` →
  `left:0; top:0; bottom:auto;` + `.agent-panel.dragged.open{transform:none}`（必须清掉 `.open` 里的
  `translate(-50%,0)`，否则再往左推半个宽度）。把手平时 `opacity:0`，hover 才显；收起态 `display:none`。
- **JS**：
  - `bindAgentDockDrag()`：拖 `.agent-head` 移动（排除按钮/下拉）。
  - `bindAgentResizeHandles()`：四角缩放，宽度走 `--agent-dock-w`、高度走 `--agent-chat-h`
    （**不写死 height** —— 面板高度是内容撑出来的，写死会把输入区压扁）。
  - 位置/尺寸存 `agentState.dockPos / dockW / chatDrawerHeight`，`applyAgentDockSize()` 负责应用。

### 踩的两个坑（都很隐蔽）
1. 🚨 **HTML 里多了一个 `</div>`**：`.agent-panel` 内部 div 层级算到 depth=0 之后又多关了一个，
   浏览器容错吞掉它，但**我的 4 个把手被甩到了 `<body>` 下**（`parentElement` 是 BODY），
   于是 `position:absolute` 相对页面定位、`:not(.chat-open)` 的隐藏规则也不生效。
   教训：**新元素没按预期定位时，先查 `parentElement`，别急着调 CSS**。
   验证手段：从 255 行开始数 `<div`/`</div>` 的 depth，出现负数就是多关了。
2. 🚨 **坐标要除 zoom**：画布启用了 `studio-scale`（整页 zoom ≈ 0.907），面板也在 zoom 列表里。
   指针事件给屏幕坐标，`style.left` 要 CSS 坐标，差一个系数。不除的话拖 160px 会跑 176px。
   更要命的是**第一次拖动**：默认布局是 `left:50% + translate(-50%)`，`offsetLeft` 是
   **加 transform 之前**的值，直接拿它当起点会横跳半个宽度。
   正确换算：`dockPos.x = offsetLeft - offsetWidth/2`（用居中关系算，**别拿 rect.left/zoom 反推**，
   取整误差会留 5px 跳动）。

### 验证
`__agent_drag_test.js` **20/20 PASS**：按下不跳 / 拖动方向 / dragged 定位 / 宽度不变形 /
dockPos 与 style.left 同坐标系 / 右下角加宽加高 / 左上角反向 / 刷新还原 / 收起态无把手 / 提示词注入。
截图：`output/ui-agent-drag-resize.png`、`ui-agent-resize-handles.png`。

## 十四、遮罩没做完就整图重绘 —— 附件图被当成「不能局部重绘」

老板原话：**「遮罩任务似乎没有做完就提前将遮罩结果发送出来了，完整的遮罩局部重绘流程不应该是这样」**。
截图里助手说：「当前这张是**消息附件而非画布节点，无法绑定局部遮罩**；我先按参考图提出局部编辑稿。」
然后生成卡标着「整图重绘」—— 用户只要求「把女人换成男人」，结果脸、构图、光线全变了。

### 根因
不是链路坏了，是**模型自己放弃了**：
- 用户把图贴在输入框（消息附件），不在【画布现状】的节点清单里；
- 模型据此判断「绑不了遮罩」→ 不给 `mask_hint` → `agentApplyAutoMask` 根本没机会跑 → 走整图重绘。
- 而 `agentPickAutoMaskNode()` 也确实只从**已有节点**里挑，不会把附件落成节点 —— 两边都缺一块。

### 修法
1. 新增 `agentEnsureAttachmentNodeForMask(userMsg)`：`agentApplyAutoMask` 里挑不到节点时，
   把 `userMsg.images[0]` 落成一个画布节点（同 url 已有节点则复用，不重复建）。
   ⚠️ 只有 `gen.inpaint === true` 才会走到，普通「参考这张画一张新的」不受影响。
2. 提示词补两处（都写明「附件图照样能局部重绘，别再说绑不了」）：
   - `AGENT_OFF_MODE_INSTRUCTION` 的【mask_hint 什么时候填】段；
   - `agentOrchestrationContext()` 的【画布能力总览】。
   🚨 注意 `AGENT_OFF_MODE_INSTRUCTION` 和 `AGENT_FORMAT_INSTRUCTION` 是**两个不同常量**，
      直接模式走后者，别只改一个。

### 验证
`__attach_mask_test.js` **9/9 PASS**：
画布 0 节点 + 只有消息附件 → 自动补出 1 个节点、写入 `node.inpaint`（crop_url / bbox / `auto:true`）、
回写 `gen.target_node`、已有遮罩不重复建、没图可改时明确 error（不静默整图重画）。
⚠️ 测试素材必须用 `/output/` 或 `/assets/` 的图 —— 后端 `output_file_from_url` 只认这两类路径，
`/static/` 的图前端能 fetch、后端读不到，会误判成「造不出遮罩」。

回归：agent_drag 20/20、autorun 9/9、default_open 13/13、dock 15/15、ui4 14/14、
inspire_clear 7/7、nogencard 17/17、askguard 9/9、emptyreply 11/11、modelstick 18/18、
sizeguard 23/23、editmsg 28/28、famsize 32/32。

### 补充：老板追问「为什么不能处理附件，agent 明明有画布控制权」

老板这句话点出了正确的心智模型：**agent 有 canvas_ops，就该能把附件落成节点再做遮罩**。
于是做了**实测**（不是只改代码），结论分两段：

**① 模型现在会给 mask_hint 了**（`__mask_llm_test.js`，真实调一次对话模型）：
输入「[图:x.png] 只把后排座椅中间那个头枕换成红色皮质，其他都不要动」+ 附件图，返回：
```json
{"intent":"edit","prompts":[{"prompt":"仅将后排座椅中间的头枕改为红色皮质…",
  "mask_hint":{"target_node":null,"bbox":[0.45,0.13,0.12,0.12]},"use_attachments":true,"use_last_outputs":true}]}
```
bbox 正好框住中间头枕 ✓ 没写 `inpaint:true` 是**设计如此**（提示词明说 mask_hint 非 null 即局部重绘，
前端 `agentApplyMaskHintInto` 会自动补 inpaint）。
⚠️ 第一次用 `__t_inpaint_base.png`（纯色方块图）测时，模型正确回答「这张图里看不到人物」并要求重传 ——
说明它**真的在看图**，不是套模板。换有内容的图才有意义。

**② 从模型返回到实发请求，整条链路通了**（`__mask_e2e_test.js`，6/6 PASS）：
```
附件图（画布 0 节点）
 → 自动补出 1 个画布节点（带附件图）
 → 写入 node.inpaint（crop_url / bbox / auto:true）
 → 实发 payload: {operation:'inpaint', inpaint:{crop_url, crop_mask_url…}}
```
- 🚨 断言别找平铺的 `crop_url`：`agentInpaintPayload` 产出的是 `{operation:'inpaint', inpaint:{...}}`。
- 🚨 思维模式产物是**待确认的 prompts**，必须调 `confirmAgentPrompt(msg)` 才会进 `runAgentGenerations`；
  只调 `processAgentLlmResult` 看不到遮罩（第一版测试就卡在这）。

**③ 为什么没让 agent 自己 create_node**：现在走「模型只给 mask_hint，系统自动落地」——
agent 只需一步（指出改哪块），不用「先建节点再改」两步走，也不会建错位置或重复建。
`agentEnsureAttachmentNodeForMask` 里有同 url 去重，已有节点就复用。
若以后改成 agent 显式建节点，**必须保留这条兜底**（模型漏字段是常态）。

## 十五、上游报错文案 + 移除拖高条 + 收起回底部

老板一次提了三件事。

### ① 「始终处于上游报错」，但正文是空的
截图里就一行「请求上游接口失败：」—— 冒号后面什么都没有。
根因：`str(httpx.ConnectTimeout())` **经常是空串**，原来 8 处 `f"请求上游接口失败：{exc}"` 全渲染成空。
- 新增 `friendly_upstream_http_error(exc)`：带**异常类名** + 目标 host + 按类型给排查方向
  （ConnectTimeout=网络/代理/地址错；ReadTimeout=上游太慢或这一轮太重；ConnectError=域名/端口/被墙；
  WriteTimeout=附件太大发不出去；RemoteProtocolError=中途断流，重试通常能好）。
- 顺手 `print("[upstream-error] ...")` 进服务日志 —— 下次再出现，日志里能直接看到是哪一类、打给谁。
- 8 处调用点批量替换（含 SSE 那条 `yield sse_event`）。
- ⚠️ 批量替换把 docstring 里的示例也替换了，记得回头修注释。

### ② 移除顶部「拖高条」
老板：「拖动对话记录顶部的展开条对话框会下移」→ 删掉 `#agentDockResize`。
调高度改由四角缩放负责，两条入口本来就冗余。`bindAgentDockResize()` 里 `if(!handle) return;` 自动安全退出。

### ③ 收起对话后「小抽AI」跑到顶部
因为上一轮的拖拽把 `dockPos` 存下来了，收起后 `.dragged` 仍生效 → 胶囊留在半空。
- 修：`applyAgentDockSize()` 里 **只有展开态才应用 `dockPos` / `dockW`**；
  收起态一律清掉 `dragged` 和 left/top，回到 CSS 默认的「底部居中」。
  `dockPos` 本身留着 —— 再展开时回到他拖过的位置。

### 踩的坑（这次最有价值的一条）
🚨 **`transition` 会让 `getBoundingClientRect()` 读到过渡起点**。
`.agent-panel` 的 `transform` 有 `.16s` 过渡，`applyAgentDockSize()` 之后**立刻**量，
拿到的是 `matrix(...,-379.996,0)`（起点）而不是 `none`（终点）→ 位置校准算反，
面板被推到 `left:-9`（屏幕外），拖动时一跳 344px（正好半个宽度）。
- 修 1：`.agent-panel.dragged { transition:none; }` —— 拖拽期间本来就不该有过渡（会「追着鼠标慢慢挪」）。
- 修 2：`agentFreezeDockPosition()` 里临时把 `style.transition='none'`、量完再还原，确保拿到终值。
- 教训：**任何「设置样式 → 立刻量位置」的代码都要先确认有没有 transition**。

## 十六、局部重绘结果落新节点，不再替换原图

老板原话：**「结果是对的，但生产的结果不应该直接替换掉原图，而是以一个新图片节点展示」**。

### 改动（`runAgentGenerations` + `recoverAgentGenerations`）
1. **inpaint 分支不再拿用户节点当占位**：改成 `agentFindEmptyPosition(1)` 建一个新节点
   （标题「局部重绘」），原节点只负责提供遮罩 / 裁切基准（`gen._inpaintNodeId` 仍然记着它，payload 要用）。
2. **不再迁遮罩**：删掉 `keepInpaintAfterRun(liveNode, _ipMeta)` 调用 ——
   原图连同遮罩保持原样，用户还能在原节点上接着改同一块，也能直接对比「改前 / 改后」。
   （`keepInpaintAfterRun` 函数本身留着，现在无调用点。）
3. **失败时删占位**：以前 `if(gen._inpaintNodeId){ liveNode.pending=0 }` 是怕删掉老板的图；
   现在占位是我们自己建的，原图压根没被碰过 ⇒ 直接删掉空节点。
4. `recoverAgentGenerations` 同步：新节点标题也按 `gen._inpaintNodeId ? '局部重绘' : ...` 走。

### 关键区分（别和 BH.8 ④ 搞混）
- **后端仍然「回贴」**：`/api/canvas-image-tasks` 把裁切重绘结果合成回**整图尺寸**再返回，
  差异只落在遮罩 bbox 内 —— 这一层没变。
- **前端不再把它塞回原节点**，而是放进新节点。
  ⇒ 以前 BH.8 ④ 那句「必须回贴」讲的是**后端合成**，不是「前端替换原图」。
